# 동작 결정 기록

기존 iOS·Android가 서로 다르게 동작하거나, 규칙 문서·서버와 어긋나거나, 버그로 보이는 곳에서 **다섯 클라이언트가 따를 동작**을 정한다. 2026-10-27 분석 기준이며 결정 주체는 이 레포(재구현 프로젝트)다. 원본 팀 레포의 규칙은 바꾸지 않는다.

각 항목: 배경(근거) → 결정 → 테스트 포인트. 근거 약어: iOS = [legacy-ios](../reference/legacy-ios.md), AN = [legacy-android](../reference/legacy-android.md), API = [api-contract](../reference/api-contract.md).

---

## D-01 제목·캡션 길이 계산

- 배경: 두 앱 모두 grapheme(사용자 인지 문자) 기준으로 10자를 자른다(iOS §5.1-2, AN §5.2-6). 서버는 `strip()` 후 **code point** 기준 10자(API §1.3, H1~H5). 규칙 POST-005는 "앞뒤 공백 제거 안 함"이라 적혀 있지만 서버 코드는 제거한다(API §8.1 D2).
- 결정: **입력값의 앞뒤 공백을 제거한 뒤 code point 수로 센다.** 10 초과면 입력을 막는다(잘라내지 않고 더 이상 입력되지 않게, 붙여넣기는 10 code point까지만 받는다). 공백만 있거나 비면 제목 없음(`null`)으로 보낸다. 표시에서 제목이 없으면 "무제".
- 공백 제거는 각 플랫폼 기본 trim(유니코드 공백, NBSP·U+3000 포함)을 쓴다. 서버 Java `strip()`은 NBSP를 지우지 않지만 클라이언트가 제거한 값을 보내므로 길이 판정은 어긋나지 않는다.
- 테스트: 이모지 10개 허용, 결합 이모지(👨‍👩‍👧, code point 5개) 2개+1자는 11 → 차단, 앞뒤 공백 포함 12자이고 strip 후 10자면 허용.

## D-02 서버 오류 분기는 errorCode + HTTP 상태 + 호출 API로만

- 배경: 두 앱이 `POST /posts` 오류를 서버 **한글 message 문자열 일치**로 분기한다(iOS §5.1-3, AN §5.2-3). 서버는 두 경우 모두 `400 BUSINESS_ERROR`라 코드로는 구분되지 않는다(API §5.2).
- 결정: 클라이언트는 `message` 문자열로 분기하지 않는다. `POST /posts`가 `400 BUSINESS_ERROR`로 실패하면 `GET /posts/today`를 다시 불러 판정한다.
  - `isPosted == true` → "이미 이 주제에 전시한 사진이 있어요." (+ 받은 postId로 성공 화면 대신 안내)
  - 404 또는 `topicDate`가 진입 때와 다름 → "주제가 변경되어 전시할 수 없어요."
  - 그 외(업로드 만료·재사용·처리 거절 등) → 서버 `message`를 그대로 보여 주고 사진 준비를 처음부터 다시 한다.
- `message`는 표시용으로만 쓴다. 알 수 없는 `errorCode`는 `BUSINESS_ERROR`로 취급한다.
- 테스트: 같은 400이라도 `/posts/today` 응답에 따라 세 문구가 갈린다. message 문자열을 바꿔도 분기가 같다.

## D-03 AI 리뷰 폴링 간격

- 배경: iOS 홈은 5초, iOS 피드·Android 전체는 3초(iOS §5.1-4). 안내 문서는 3초.
- 결정: **모든 화면 3초 간격, 300초 창.** 창 시작은 POST를 보낸 시각 또는 화면에 들어와 폴링을 시작한 시각. 창이 끝나면 조용히 멈추고 "처리가 오래 걸리고 있어요. 나중에 다시 확인해 주세요."를 보여 준다(실패 아님, POST 다시 보내지 않음). 화면이 보이지 않으면(백그라운드, 다른 화면) 멈추고, 다시 보이면 GET부터 새 창을 시작한다.
- 용어는 사용자 문구에서 "AI 피드백"으로 통일한다(iOS 홈의 "AI 리뷰" 문구 제외).
- 테스트: 가짜 시계로 2.9초에 요청 없음, 3초에 1회, 300초 후 중단, 화면 이탈 시 중단.

## D-04 좋아요는 모든 화면에서 낙관적 갱신 + 실패 시 롤백·토스트

- 배경: iOS 전시는 서버 확정형, iOS 피드·Android는 낙관적. Android 피드는 실패 시 무음 롤백, 전시는 토스트(iOS §5.1-5, AN §5.2-4).
- 결정: 전시·홈 랭킹·피드 모두 **누르는 즉시 상태와 개수를 바꾸고**, 실패하면 이전 상태로 되돌리고 "좋아요를 반영하지 못했어요" 토스트를 띄운다. 성공 응답의 `likeCount`·`isLiked`로 덮어쓴다. 같은 게시물에 요청이 진행 중이면 마지막 의도만 남기고 직렬화한다(진행 중 연타는 요청을 쌓지 않고, 응답 후 최종 의도와 서버 상태가 다르면 한 번 더 보낸다). 늦게 도착한 목록 재검증 응답이 완료된 좋아요 상태를 덮지 않는다.
- 404 응답이면 롤백 후 해당 게시물을 목록에서 뺀다(삭제·비공개).
- 테스트: 즉시 반영, 실패 롤백 + 토스트, 연타 3회 후 서버 최종 상태 일치, 늦은 재검증 응답 무시.

## D-05 게스트 제한

- 배경: iOS는 전시 탭과 피드 진입을 게스트에게 열어 두지만 좋아요가 401로 실패한다. Android는 피드 진입을 막는다(iOS §1.3, AN §1.2). 서버는 `GET /posts`(목록)만 비로그인 허용, 상세는 401(API §0.1).
- 결정: 게스트는 홈(공개 랭킹·배너·오늘 주제), 전시 탭(목록)을 볼 수 있다. 아래는 API를 호출하지 않고 토스트로 막는다.

  | 동작 | 문구 |
  | --- | --- |
  | 기록 탭 | 기록을 보려면 로그인이 필요해요 |
  | 업로드 버튼 | 게시물을 추가하려면 로그인이 필요해요 |
  | 게시물 상세(피드) 진입 | 게시물 피드를 보려면 로그인이 필요해요 |
  | 좋아요 | 좋아요를 누르려면 로그인이 필요해요 |
  | 알림 진입 | 로그인 후 알림을 확인할 수 있어요 |
  | 피드백 | 피드백을 보내려면 로그인이 필요해요 |

  설정 탭에서 게스트는 "로그인" 버튼만 보이며, 누르면 게스트 플래그를 지우고 로그인 화면으로 간다.
- 테스트: 게스트 상태에서 각 동작이 네트워크 요청 0건 + 해당 토스트.

## D-06 홈 히어로 상태

- 배경: iOS는 반려(REJECTED) 히어로를 만들지 못해 "사진 상태를 불러오지 못했어요"가 뜬다(iOS §5.1-1). 서버의 `GET /posts/today`는 반려되면 `isPosted=false`를 주고, 캘린더도 REJECTED를 빼고 준다(API C1).
- 결정: 히어로는 `GET /posts/today`로 정한다(게스트는 호출하지 않고 Empty).

  | 조건 | 상태 | 문구 |
  | --- | --- | --- |
  | 로딩 중 | Loading | 오늘의 주제를 불러오는 중 |
  | 404 | NoOpenTopic | 지금은 참여할 수 있는 주제가 없어요 |
  | `isPosted=false` | Empty | "{주제}" 사진을 공유하지 않았어요 (+ 업로드 진입) |
  | `VALIDATING` | Processing | 사진을 처리하고 있어요 |
  | `PENDING` | Photo + "검수 대기" 배지 | |
  | `APPROVED` | Photo | |
  | 403(정지) | Empty와 같지만 업로드 진입 시 정지 안내(D-08) | |
  | 그 외 실패 | Error + 다시 시도 | 사진 상태를 불러오지 못했어요 |

  사진 썸네일은 이번 주 기록(캘린더) 응답에서 같은 postId를 찾아 쓴다. 반려는 홈에서 따로 표시하지 않는다(Empty가 되어 다시 올릴 수 있다). 반려 사실은 알림으로 안다.
- 테스트: 각 응답 → 상태 매핑, 반려 후 Empty.

## D-07 게시물 생성 응답 유실 복구(POST-011)

- 배경: 두 앱 모두 `POST /posts` 타임아웃 뒤 재확인이 없다(AN §5.2-11).
- 결정: `POST /posts`는 자동 재시도하지 않는다. 응답을 못 받으면(타임아웃·연결 끊김) `GET /posts/today`를 불러 `isPosted=true`면 성공으로 처리해 성공 화면으로 간다(상태는 응답의 `moderationStatus`). `isPosted=false`면 "네트워크 연결을 확인해 주세요."와 함께 다시 제출할 수 있게 한다(업로드 ID는 1시간 유효하므로 그대로 재사용).
- 테스트: POST 타임아웃 + today isPosted=true → 성공 화면 1회, isPosted=false → 재제출 가능, 같은 uploadId 재사용.

## D-08 정지(BANNED) 회원

- 배경: 정지 회원은 로그인은 되고 쓰기 API만 `403 FORBIDDEN`(API §2.6). `GET /posts/today`도 403.
- 결정: 로그인 직후 따로 안내하지 않는다(규칙 미정, open-questions Q-09). 403을 받는 곳마다 아래 문구를 보여 주고 같은 요청을 다시 보내지 않는다.

  | 위치 | 문구 |
  | --- | --- |
  | 업로드 진입 | 이용이 정지되어 게시물을 작성할 수 없어요. |
  | AI 피드백 요청 | 이용이 제한되어 AI 피드백을 요청할 수 없어요. |
  | 좋아요 등록 | 이용이 제한되어 좋아요를 누를 수 없어요. (롤백 포함) |
  | 사인 변경 | 이용이 제한되어 사인을 변경할 수 없어요. |
  | 제목 수정 | 이용이 제한되어 제목을 수정할 수 없어요. |
  | 홈 히어로(`/posts/today` 403) | Empty로 표시, 업로드 진입 시 위 문구 |

  좋아요·사인·제목 수정 문구는 기존 앱에 없던 신규 문구다.

  게시물 수정·삭제의 403은 "본인의 게시물만 수정할 수 있어요" / "본인이 작성한 게시물만 삭제할 수 있어요"이지만, 화면에서 버튼을 본인 게시물에만 보이므로 정상 흐름에서는 나오지 않는다. 403 응답의 문구 구분은 호출한 API로 한다(D-02).
- 테스트: 각 API 403 fixture → 문구, 재요청 0건.

## D-09 알림 시각 표시

- 배경: iOS 알림 시각만 기기 시간대, 나머지는 KST(iOS §5.1-6).
- 결정: **모든 날짜·시각을 KST로 표시**한다. 알림 시각 형식은 "M월 d일 HH:mm".
- 테스트: 기기 시간대를 UTC·America/Los_Angeles로 바꿔도 같은 문자열.

## D-10 알림 미읽음 표시

- 배경: 두 앱 모두 `GET /notifications/unread-status`를 부르지만 Android는 표시하지 않는다(AN §5.2-7).
- 결정: 홈 상단 알림 버튼에 미읽음 점을 표시한다. 홈이 보일 때, 앱이 포그라운드로 올 때, 알림함에서 돌아올 때, 푸시를 받았을 때 다시 조회한다. 게스트는 조회하지 않는다.

## D-11 푸시 탭 처리

- 배경: 기존 두 앱의 목적지는 거의 같지만 읽음 실패 처리와 로그아웃 상태 처리가 다르다(iOS §1.4, AN §1.5).
- 결정:
  1. 목적지 표

     | `type` | 이동 | 읽음 |
     | --- | --- | --- |
     | `TOPIC` | 홈(맨 위 + 새로고침). 이미 홈이면 중복 이동 안 함 | 안 함(notificationId 없음) |
     | `REMINDER` | 홈 | 안 함 |
     | `POST_APPROVED` | 게시물 상세(`sourceId`, 내 게시물) | 단건 읽음 후 이동 |
     | `AI_REVIEW_COMPLETED`, `AI_REVIEW_FAILED` | 게시물 상세 + AI 피드백 시트 자동 열기(최신 GET 기준 1회) | 단건 읽음 후 이동 |
     | `POST_REJECTED`, `NOTICE` | 알림 상세(`notificationId`) | 단건 읽음 후 이동 |
     | 알 수 없는 type, 필드 누락, UUID 형식 아님 | 알림함 목록 | 안 함 |

  2. 읽음 처리 결과: 성공 → 이동. 네트워크 실패 → 토스트 "읽음 상태를 저장하지 못했어요. 네트워크 연결을 확인해 주세요." 후 **이동함**. 404 → 토스트 "더 이상 확인할 수 없는 알림이에요." + 알림함·미읽음 새로고침, **이동 안 함**. 그 외 실패 → 404와 같게 처리.
  3. 로그아웃·게스트 상태에서 탭하면 버린다(앱만 열림). 로그인·약관·사인 화면이나 업로드·피드백 작성 중이면 그 화면을 벗어날 때까지 보류했다가 처리한다. 콜드 스타트 탭은 메인이 준비될 때까지 보류한다.
  4. 같은 게시물 상세가 이미 열려 있으면 새로 쌓지 않고 교체한다.
- 테스트: type별 목적지, 읽음 성공/네트워크 실패/404 분기, 로그아웃 상태 무시, 작성 중 보류.

## D-12 최초 전시일

- 배경: 두 앱이 `2026-09-17`을 하드코딩(서버 API 없음, API §8.2-21).
- 결정: 공통 상수 `FIRST_TOPIC_DATE = 2026-09-17`. 전시 날짜 이동·선택의 하한이다. 서버에서 그 날짜에 주제가 없으면(404) 기존 전시를 유지하고 빈 상태를 보여 준다.

## D-13 사진 편집 필터

- 배경: 필터 목록이 다르다. iOS: 원본, 선명, 크롬, 페이드, 흑백, 누아르. Android: 원본, 흑백, 따뜻하게, 차갑게, 빈티지, 선명하게(iOS §2.9, AN §2.8). 조정 항목과 자르기 비율은 같다.
- 결정: **Android 목록을 기준으로 한다**(원본, 흑백, 따뜻하게, 차갑게, 빈티지, 선명하게). Android는 4×5 컬러 행렬로 정의돼 있어 다섯 플랫폼에서 같은 수식으로 재현하기 쉽다. 행렬 값은 원본 레포 `client/android/docs/architecture/photo-edit.md`와 Android 소스에서 옮겨 `shared/photo-edit/filters.json`에 둔다. 조정: 노출(±1.5EV), 대비, 하이라이트, 그림자, 블랙 포인트(범위 0.3), 채도, 따뜻함(gain 0.25), 자동 보정(강도 0~1). 자르기 비율: 원본, 자유, 1:1, 4:5, 5:4, 3:4, 4:3, 9:16, 16:9, 90도 회전, 초기화.
- 편집 결과는 한 번만 손실 압축한다(iOS의 JPEG q1.0 → WebP 이중 인코딩을 하지 않는다, iOS §5.1-11). EXIF는 회전만 반영하고 메타데이터는 제거한다.
- 테스트: 같은 입력 이미지 + 같은 필터 → 플랫폼 간 픽셀 차이 허용 범위(평균 ΔE ≤ 3, 스크린샷 비교) 안.

## D-14 업로드 진입·업로드 흐름

- 결정(두 앱 공통 동작을 정식화):
  1. 업로드 버튼 → (게스트면 D-05) → `GET /posts/today`. 확인 중 연타는 1회만. `isPosted`이면 "이미 이 주제에 게시물을 작성했어요.", 404 "지금 참여할 수 있는 주제가 없어요.", 403 D-08, 401 로그인 화면, 그 외 "게시물 작성 여부를 확인하지 못했어요. 다시 시도해 주세요.".
  2. 통과하면 응답 `topicDate`를 업로드 화면에 고정한다(자정이 지나도 진입 때 주제로 제출). `GET /topics?date=topicDate`로 `topicId`와 제목을 얻는다.
  3. 사진을 고르거나 편집을 마치면 바로 백그라운드에서 `POST /posts/uploads` 정책 발급과 WebP 인코딩을 시작한다. 정책 `contentType`이 `image/webp`가 아니면 실패.
  4. "전시하기" → 준비가 끝날 때까지 기다린 뒤 → URL 만료 5초 전이면 새 정책 발급(새 `maxBytes`가 더 작으면 다시 인코딩) → presigned `PUT`(인증 헤더 없음, `Content-Type`은 정책값) → `POST /posts`.
  5. 제출 중 연타는 1회만. 실패 시 입력(사진, 제목)은 유지.
  6. 성공 화면: "‘{주제}’을/를 기록했어요."(받침으로 조사 선택), PENDING이면 "검수를 기다리고 있어요. 피드 표시까지 시간이 조금 걸릴 수도 있어요!", VALIDATING이면 "사진을 확인하고 있어요. 피드 표시까지 시간이 조금 걸릴 수도 있어요!", 버튼 "확인했어요." → 업로드한 날짜의 전시.
- 카메라: 앱은 시스템 카메라(또는 플랫폼 카메라 UI)를 쓰고, 촬영본은 기기 앨범에 저장한다. 저장 실패는 토스트 "사진을 갤러리에 저장하지 못했어요."만 띄우고 업로드는 계속 가능. 앨범 선택은 권한이 필요 없는 시스템 선택기를 쓴다. 카메라가 없는 기기·웹 데스크톱에서는 카메라 버튼을 숨긴다.

## D-15 강제 업데이트

- 배경: iOS는 iTunes lookup으로 major/minor만 비교, Android는 Play In-App Update priority ≥ 1(iOS §1.2, AN §1.3). 서버 규칙 없음(API §8.2-17).
- 결정: 플랫폼별로 둔다. iOS native·Flutter(iOS)·RN(iOS)는 iTunes lookup 방식, Android native·Flutter(Android)·RN(Android)는 Play In-App Update 방식, Web은 게이트 없음(새 배포는 새로고침으로 반영). 조회 실패·오프라인이면 통과한다(Android의 "온라인인데 확인 실패면 차단"은 따르지 않는다. 스토어 장애로 앱을 막지 않기 위해). 이 레포 앱은 스토어에 올리지 않으므로 **게이트 로직과 테스트만 만들고 실제 조회는 설정으로 끈다**.
- 다이얼로그 문구: "업데이트가 필요해요" / "원활한 서비스 이용을 위해 최신 버전으로 업데이트해 주세요." / "업데이트". 닫을 수 없다.

## D-16 로그아웃·탈퇴

- 로그아웃: 확인 "정말 로그아웃 하시겠습니까?" → 로컬 토큰·캐시를 먼저 지우고 → `POST /auth/logout {refreshToken}`(실패 무시) → 로그인 화면. 푸시 기기 해제 API는 없다(서버가 세션과 함께 지운다).
- 탈퇴: 확인 "정말 회원탈퇴 하시겠습니까?" → `DELETE /users/me` → 204일 때만 로컬 정리 후 로그인 화면. 실패하면 세션을 유지하고 토스트 "요청을 처리하지 못했어요. 다시 시도해 주세요.".
- 카카오 SDK 연결 해제(unlink)는 하지 않는다(서버도 안 함, open-questions Q-05).

## D-17 토큰 저장·갱신

- 저장: userId, accessToken, accessToken 만료 시각, refreshToken, refreshToken 만료 시각, 게스트 플래그. 토큰은 플랫폼 보안 저장소(iOS Keychain, Android Keystore 암호화, Flutter `flutter_secure_storage`, RN `expo-secure-store`/Keychain, Web은 open-questions Q-03 결론 전까지 메모리 + `sessionStorage` 금지 원칙의 임시안).
- 갱신: 만료된 access token은 헤더에 붙이지 않는다. 401 `UNAUTHORIZED`이고 토큰을 보냈던 요청만 갱신한다(게스트 요청의 401은 갱신하지 않음). 갱신은 single-flight(동시 401은 하나의 refresh를 공유). 갱신 사이에 토큰이 이미 바뀌었으면 refresh 없이 새 토큰으로 재시도. 원 요청은 1회만 재전송.
- refresh 응답의 두 토큰을 즉시 함께 저장한다. refresh 요청은 자동 재시도하지 않는다. `401 REAUTHENTICATION_REQUIRED`(refresh 응답이든 일반 API든)만 세션을 지우고 로그인 화면으로 보낸다. 네트워크·5xx로 refresh가 실패하면 그 요청만 실패시키고 로그아웃하지 않는다.
- 갱신 도중 로그아웃·계정 전환이 일어나면 갱신 결과를 저장하지 않는다.

## D-18 사인 변경 결과 표시

- 배경: Android는 변경 후 썸네일 자리에 원본 URL을 넣는다(AN §5.2-1). 서버는 처리 전까지 기존 사인 URL을 돌려준다(API §3.2).
- 결정: 변경 요청 성공 후 토스트 "사인 반영까지 시간이 좀 걸릴 수 있어요!"를 띄우고, 설정의 사인 카드는 `GET /users/me/signature`를 다시 불러 그 썸네일을 쓴다(썸네일이 null이면 원본). 화면이 다시 보일 때마다 재조회한다.

## D-19 기록 탭의 "현재 달"

- 배경: Android `INITIAL_RECORD_MONTH`가 프로세스 시작 시 고정(AN §5.2-2).
- 결정: 현재 달은 화면 진입·포그라운드 복귀 때마다 KST 기준으로 다시 계산한다. 월 목록(`/posts/calendar/months`)에 현재 달이 없어도 선택지에 넣는다.

## D-20 오류 화면과 토스트

- 이미 콘텐츠가 보이는 상태에서 새로고침·다음 페이지가 실패하면 콘텐츠를 유지하고 토스트만 띄운다. 콘텐츠가 없으면 오류 화면 + "다시 시도".
- 토스트는 화면이 보일 때만 띄우고, 같은 문구가 연달아 나와도 다시 띄운다(메시지마다 고유 ID).
- 네트워크 오류(연결 실패·타임아웃) 문구는 "네트워크 연결을 확인해 주세요."로 통일한다.
- 요청 취소(화면 이탈)는 오류로 보이지 않는다.

## D-21 네트워크 타임아웃

- 배경: iOS·Android 모두 기본값(iOS 60초, OkHttp 10초).
- 결정: 일반 API 연결 10초·응답 15초, presigned PUT은 60초. 멱등 요청(GET, PUT, DELETE, PATCH, 업로드 정책 발급)만 네트워크 오류·5xx에 지수 백오프(0.5초, 1초) 최대 2회 재시도한다. `POST /posts`, `POST /auth/refresh`, `POST /feedbacks`, `POST .../ai-review`, `POST /auth/social-*`는 자동 재시도하지 않는다. 429·503의 `Retry-After`가 있으면 그만큼 기다린다. 단 `RETRY_AFTER_MAX_MS`(30초, 임시 상한)를 넘으면 기다리지 않고 그 응답으로 실패 처리한다(2026-10-27 Web 스레드 제안, 다섯 플랫폼 공통).

## D-22 분석 이벤트

- 결정: 두 앱 화면 이름의 합집합으로 `screen_view`를 수동 전송한다: `login`, `terms`, `terms_of_service`, `privacy_policy`, `onboarding_signature`, `onboarding_signature_preview`, `change_signature`, `change_signature_preview`, `home`, `issue`, `notifications`, `notification_detail`, `display`, `feed`, `record`, `settings`, `feedback`, `photo_upload`, `photo_upload_success`. 탭 선택 시 `bottom_navigation_selected {destination: home|display|record|settings}`. 분석은 `AnalyticsTracker` 인터페이스 뒤에 두고, 이 레포에서는 기본 구현을 로그 출력(또는 Firebase 설정이 있을 때만 Firebase)으로 한다.

## D-23 게시물 상세의 수정·삭제 버튼

- 결정: 내 게시물이고 주제가 오늘(KST, 상세의 `topic.topicDate`)일 때만 제목 수정 버튼을 보인다. 삭제는 내 게시물이면 보인다(상세는 PENDING·APPROVED만 보이므로 삭제 가능 상태). 삭제 성공 → 이전 화면으로 돌아가 목록·기록·홈에서 해당 게시물을 빼고 토스트 "게시물을 삭제했어요".
- 오류 문구는 AN §2.7 표를 따른다(400 "삭제할 수 없는 상태의 게시물이에요", 404 "게시물을 찾을 수 없어요" 등).

## D-24 알림 읽음 404 문구

- 배경: Android 알림함 항목 탭 404 문구가 "삭제된 게시물입니다"로 고정(AN §5.2-19).
- 결정: 알림함 항목 탭과 푸시 탭 모두 404이면 "더 이상 확인할 수 없는 알림이에요."로 통일하고 목록·미읽음을 새로고침한다.

## D-25 약관 동의

- 배경: 두 앱 모두 동의를 로컬 상태로만 가진다. 서버 가입 API에 동의 필드가 없다(API §8.2-1).
- 결정: 기존과 같이 두 필수 항목 동의 전에는 "다음"을 막고, 동의 사실은 저장·전송하지 않는다. 약관 문서는 Notion URL을 앱 안 웹뷰(웹은 새 탭)로 연다. 허용 호스트: `notion.com`, `notion.so`, `notion.site`의 https만, 나머지는 외부 브라우저. URL은 공통 상수로 둔다.

## D-26 게시물 상세의 내 게시물 판정

- 배경: `GET /posts/{id}` 응답에는 `isMine`이 없고 `authorId`가 있다(서버 `PostDetailResponse`). 기존 앱은 진입 경로(전시 목록의 `isMine`, 기록·푸시는 내 것)로 판정했다.
- 결정: 상세 응답을 받으면 **`authorId == 저장된 userId`로 판정**한다. 응답 전에는 진입 경로 값을 임시로 쓰되(목록 `isMine`, 기록·푸시 진입은 true), 응답이 오면 응답 기준으로 바꾼다. 게스트는 항상 false.
- 테스트: 기록에서 진입 + `authorId`가 내 id → 수정·삭제 버튼 유지, 진입 값과 응답이 다르면 응답 기준.
