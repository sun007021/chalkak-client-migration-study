# 에이전트 시나리오: SET, FDBK

[catalog/settings-feedback.md](../catalog/settings-feedback.md)에서 구분이 `A`인 TC를 서브에이전트가 시뮬레이터·에뮬레이터·브라우저와 개발 서버에서 직접 확인하는 절차다. 공통 전제(개발 서버 주소, 테스트 계정은 "실행 시 사용자에게 받은 계정", 비밀값 비기록, 사용자 Mac에서 실행, 결과를 parity-matrix에 반영)는 [boot-auth.md의 공통 전제](boot-auth.md#공통-전제-이-문서의-모든-시나리오)와 같다. 회원탈퇴 시나리오는 [boot-auth.md의 AG-AUTH-004](boot-auth.md)에 있으며 **사용자 확인 없이 실행하지 않는다.**

## SET

### AG-SET-001 OS 알림이 꺼진 상태에서 서버 토글을 켤 때 시스템 설정 이동

- 대응 TC: TC-SET-054
- 사전 조건: 로그인된 회원(실행 시 사용자에게 받은 계정). OS 알림 권한이 **차단된** 상태를 만든다: iOS 시뮬레이터는 최초 권한 다이얼로그에서 "허용 안 함" 선택, Android 13+ 에뮬레이터는 "허용 안 함"을 두 번 선택하거나 설정 앱에서 앱 알림 끄기. 서버 설정 3개 중 하나(예: AI 피드백 완료 알림)를 꺼 둔다. 개발 서버 정상.
- 단계:
  1. 설정 탭을 열어 OS 권한 행이 없고 서버 토글 3개만 있는지 캡처한다.
  2. 꺼져 있는 "AI 피드백 완료 알림" 토글을 켠다.
  3. 시스템 알림 설정 화면(앱 알림 설정)으로 이동했는지 확인한다. 이동했다면 화면을 캡처하고 OS 설정에서 알림을 허용으로 바꾼다.
  4. 앱으로 돌아와 토글 상태가 서버 값(사용자에게 받은 토큰으로 `GET /notification-settings` 읽기 전용 조회)과 일치하는지 확인한다.
  5. OS 권한이 **허용**된 상태에서 같은 토글을 껐다 켜서 시스템 설정으로 이동하지 않고 서버 PATCH만 일어나는지 확인한다.
  6. 모든 토글을 켠 상태(초기값)로 원복한다.
- 기대 결과: OS 차단 상태에서 토글을 켜면 시스템 알림 설정으로 이동한다. 허용 상태에서는 이동 없이 서버 설정만 바뀐다. 이동 전후 앱이 크래시하지 않고 토글 상태가 서버 값과 일치한다. 서버 PATCH가 이동 시점에도 보내지는지는 기록해 기능 문서 확정(TC-SET-038의 미정 사항)에 반영한다.
- 확인 방법: 스크린샷(설정 탭, 시스템 설정 화면, 복귀 후), 디버그 로그에서 PATCH /notification-settings 호출 유무와 바디, 서버 조회 결과.
- 되돌릴 수 없음: 아니오(설정 값은 6단계에서 원복. OS 권한 변경은 시뮬레이터에서 복원 가능).
- 플랫폼 차이: iOS는 앱 설정 화면(`openSettingsURLString`), Android는 앱 알림 설정(`ACTION_APP_NOTIFICATION_SETTINGS`), Android 12 이하는 OS 런타임 권한이 없어 이동 조건이 달라질 수 있다. Web은 이 시나리오를 수행하지 않는다(OS 권한 이동 없음, TC-SET-040 결정에 따름).

### AG-SET-002 실제 Notion 약관·개인정보 문서 열기 (설정 경로)

- 대응 TC: TC-SET-055
- 사전 조건: 로그인된 회원. 시뮬레이터가 인터넷에 연결됨. 개발 서버는 필요하지 않다.
- 단계:
  1. 설정 탭의 "이용약관"을 탭해 문서가 열리는 시간과 본문을 확인한다. 스크롤하고 문서 내 링크 하나를 탭한다.
  2. 닫기(시트 닫기, 뒤로가기, Web은 탭 닫기)로 설정 탭에 돌아오는지 확인한다.
  3. "개인정보처리방침"도 1~2를 반복한다.
  4. 네트워크를 끊고 열어 "문서를 불러오지 못했어요"와 "다시 시도"를 확인하고, 복구 후 다시 시도로 문서를 연다.
  5. 가입 화면의 약관 문서와 같은 문서가 열리는지 AG-ONB-002의 결과와 비교한다.
- 기대 결과: 문서가 읽을 수 있게 열리고 닫으면 설정 탭이 유지된다. 허용 호스트만 앱 안에서 열린다. 가입 약관과 같은 문서. 오프라인은 오류와 다시 시도.
- 확인 방법: 스크린샷, 디버그 로그에서 열린 URL의 호스트와 scheme, screen_view `terms_of_service`, `privacy_policy`.
- 되돌릴 수 없음: 아니오.
- 플랫폼 차이: iOS WKWebView 시트, Android WebView 다이얼로그, Flutter·RN 웹뷰 패키지, Web 새 탭. 문서 렌더링 차이는 기록만 한다.

### AG-SET-003 푸시 수신 설정 실서버 왕복과 재시작 후 유지

- 대응 TC: TC-SET-056
- 사전 조건: 로그인된 회원(실행 시 사용자에게 받은 계정). 서버 설정이 초기값(모두 켜짐)임을 먼저 `GET /notification-settings`(읽기 전용, 사용자에게 받은 토큰)로 기록한다. 개발 서버 정상.
- 단계:
  1. 설정 탭에서 "오늘 주제 알림"을 끈다. 토글이 즉시 꺼지고 서버 조회가 topicPushEnabled false, 나머지 true인지 확인한다.
  2. "게시물 승인·반려 알림"을 끈다. 서버 조회가 두 항목 false인지 확인한다.
  3. 앱을 강제 종료 후 다시 열어 설정 탭의 토글이 서버 값과 같은지 확인한다.
  4. 두 토글을 빠르게(1초 안에) 연속으로 바꿔 보고 최종 UI 상태와 서버 값이 일치하는지 확인한다.
  5. 네트워크를 끊은 채 토글을 바꿔 이전 값으로 되돌아오고 토스트("알림 설정을 저장하지 못했어요. 다시 시도해 주세요.")가 뜨는지 확인한다. 네트워크를 복구한다.
  6. 모든 토글을 켜서 초기값으로 원복하고 서버 조회로 확인한다.
- 기대 결과: 토글 변경이 바로 UI에 반영되고 서버에도 항목별로 저장된다. 재시작 후 서버 값과 일치. 연속 토글 후 최종 상태가 일치. 오프라인 실패는 해당 항목만 롤백 + 토스트. 원복 가능.
- 확인 방법: 단계별 스크린샷, 서버 조회 결과 표(단계별 3개 값), 디버그 로그에서 PATCH 바디가 변경한 항목 하나뿐인지.
- 되돌릴 수 없음: 아니오(설정은 되돌릴 수 있다. 단 서버에 변경 이력은 남지 않으므로 6단계 원복을 반드시 수행한다).
- 플랫폼 차이: iOS 시뮬레이터, Android 에뮬레이터, 웹 브라우저. Web에서 푸시 설정 카드를 보이는지는 TC-SET-040 결정에 따라 수행 여부를 정한다.

## FDBK

### AG-FDBK-001 실서버 피드백 전송

- 대응 TC: TC-FDBK-036
- 사전 조건: **이 시나리오는 서버에 피드백이 영구 저장되므로 실행 전에 사용자에게 알리고 허용을 받는다.** 로그인된 회원(실행 시 사용자에게 받은 계정). 개발 서버 정상. 피드백 내용은 개인정보 없이 "테스트: 클라이언트 재구현 검증 (플랫폼명, 날짜)" 같은 식별 가능한 문구로 한 건만 쓴다.
- 단계:
  1. 설정 탭 → "피드백 보내기"를 연다.
  2. 빈 상태와 공백만 입력한 상태에서 "보내기"가 비활성인지 확인한다.
  3. 테스트 문구를 입력한다. 글자 수 카운터가 입력한 글자 수와 같은지 확인한다.
  4. "보내기"를 누르고 "보내는 중..." 상태를 캡처한다.
  5. 성공 토스트 "피드백을 보내주셔서 감사해요."가 뜨고 화면이 닫히는지, 다시 열었을 때 입력이 비어 있는지 확인한다.
  6. 디버그 로그에서 POST /feedbacks 상태가 201이고 응답에 feedbackId와 createdAt이 있는지 확인한다. 응답 값 자체는 기록하지 않고 존재 여부만 기록한다.
- 기대 결과: 요청 1회, 201, 성공 토스트와 화면 닫힘, 재진입 시 빈 입력. 이중 전송이 없다.
- 확인 방법: 스크린샷, 디버그 로그(요청 횟수 1회, 상태 201). 서버에는 사용자 조회 API가 없으므로(FEEDBACK-003) 서버 측 저장 확인은 사용자에게 관리자 콘솔에서 확인하도록 요청하거나 건너뛴다고 기록한다.
- 되돌릴 수 없음: 예(피드백은 수정·삭제가 불가하고 탈퇴해도 남는다). 플랫폼마다 한 건씩만 보내고 총 건수를 사용자에게 알린다.
- 플랫폼 차이: iOS 시뮬레이터, Android 에뮬레이터, 웹 브라우저. 5개 플랫폼 모두에서 보낼 필요는 없고 사용자와 합의한 대표 2곳(예: 모바일 1, Web 1)에서만 보내고 나머지는 자동 TC(TC-FDBK-015~017)로 갈음한다고 기록한다.

### AG-FDBK-002 한글 IME 조합·이모지 키보드 입력감

- 대응 TC: TC-FDBK-037
- 사전 조건: 로그인된 회원 또는 서버 호출이 필요 없는 입력 단계까지만 수행(전송하지 않음). 시뮬레이터/에뮬레이터는 한국어 키보드를 추가한 상태(iOS는 한국어, 이모지 키보드, Android는 Gboard 한국어). 웹은 OS IME.
- 단계:
  1. 피드백 입력창에 한글을 천천히/빠르게 입력하며 조합 중인 글자(예: "ㅎ" → "하" → "한")에서 글자 수 카운터와 "보내기" 활성 상태가 튀지 않는지 본다.
  2. 이모지 키보드로 이모지 20개를 입력하고 카운터가 code point 기준으로 증가하는지 확인한다.
  3. 결합 이모지(👨‍👩‍👧)를 입력하고 카운터가 5로 늘어나는지 확인한다.
  4. 여러 줄 입력, 맨 앞뒤 공백 입력 후 카운터가 trim 후 개수를 보이는지 확인한다.
  5. 긴 문장을 붙여넣어 1000자를 넘겼을 때 화면 반응과 검증 문구를 본다. 전송은 하지 않는다.
  6. 키보드가 올라와 있을 때 "보내기" 버튼과 입력창이 가려지지 않는지, 화면 회전 또는 앱 전환 후 입력이 유지되는지 확인한다.
- 기대 결과: 조합 중에도 카운터가 깨지거나 버튼 활성이 깜박이지 않는다. code point 기준 카운트. 키보드가 입력창을 가리지 않는다. 입력은 유지된다.
- 확인 방법: 단계별 스크린샷과 화면 녹화(조합 중 프레임), 카운터 값과 입력 내용의 code point 수를 에이전트가 계산해 대조.
- 되돌릴 수 없음: 아니오(전송하지 않음).
- 플랫폼 차이: IME 동작이 플랫폼마다 다르다(iOS의 조합 중 마킹 텍스트, Android의 컴포징 스팬, Web의 compositionstart/end, Flutter·RN의 TextField 처리). 플랫폼별 이상 현상을 따로 기록한다.
