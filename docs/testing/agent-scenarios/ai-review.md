# 에이전트 시나리오: AI 피드백(AIR)

실제 AI 처리 완료(수 분)와 실제 푸시 도착은 자동화할 수 없어 서브에이전트가 확인한다. 대응 TC는 [catalog/ai-review.md](../catalog/ai-review.md)이다. 요청은 게시물당 3회로 제한되고 되돌릴 수 없다.
공통 규칙(모든 시나리오): 서버는 개발 서버 `https://chalkak-dev.pysun.kr/api/v1/`이다. 테스트 계정은 **실행 시 사용자에게 받은 카카오 계정**을 쓰며 문서·로그·스크린샷 파일명·커밋에 계정 정보와 토큰을 적지 않는다. 서버 API 조회가 필요하면 앱 디버그 로그나 사용자가 알려 준 값을 환경변수(`CHALKAK_ACCESS_TOKEN` 등)로만 다루고 출력에 남기지 않는다. 클라우드 컨테이너의 `curl`은 프록시 때문에 개발 서버에 닿지 않으므로(strategy §6) 사용자 Mac의 시뮬레이터·에뮬레이터와 Mac 터미널에서 실행한다. 스크린샷은 `agent-runs/<날짜>/<플랫폼>/AG-<영역>-NNN-<단계>.png`처럼 저장하고 계정 정보가 보이면 가린다. 결과는 패리티 매트릭스의 `A✓`로 기록한다. 플랫폼은 iOS, Android, Flutter(iOS·Android), React Native(iOS·Android), Web 순서로 같은 시나리오를 수행하고, 아래 "플랫폼 차이"에 적은 곳만 단계가 다르다.

### AG-AIR-001 실제 AI 피드백 요청부터 완료까지

- **대응 TC**: TC-AIR-060
- **사전 조건**:
  - **오늘 주제의 내 게시물이 APPROVED**여야 한다(AI 피드백은 공개된 게시물에만 요청할 수 있고 앱은 오늘 사진만 요청을 허용한다). 관리자 승인은 사람이 해야 하므로 승인 전이면 사용자에게 승인 요청을 안내하고 이 시나리오를 보류한다.
  - 해당 게시물의 AI 리뷰 요청 횟수가 3회 미만이다(상태 NONE이 가장 좋다).
  - 로그인 상태이고 가능하면 푸시 권한이 허용돼 있다.
- **단계**:
  1. 홈 AI 카드 또는 게시물 상세의 "AI 피드백 받기"를 누르고 시작 시트의 문구를 스크린샷으로 남긴다.
  2. "분석 시작하기"를 눌러 상태가 "AI 분석중"으로 바뀌는지 본다. 이때 시각을 기록한다.
  3. 앱 로그(또는 프록시)에서 `GET /posts/{id}/ai-review`가 약 3초 간격으로 나가는지 몇 건 확인한다.
  4. 완료될 때까지 기다린다(보통 수십 초~수 분, 최악 약 6분). 5분이 지나도 완료되지 않으면 "처리가 오래 걸리고 있어요…" 안내가 뜨는지 확인한다(이때 POST가 추가로 나가지 않아야 한다).
  5. 완료되면 "AI 피드백 보기"로 결과 시트를 열어 점수, 요약, 좋았던 점/아쉬운 점/다음엔 이렇게, 배지 여부를 스크린샷으로 남긴다.
  6. 알림함에 AI 피드백 완료 항목이 생겼는지 확인한다.
- **기대 결과**(관찰 가능한 것):
  - 상태가 NONE → 분석중 → 완료로 바뀌고 폴링이 완료 시점에 멈춘다.
  - 결과의 점수는 0~10 소수 첫째 자리, 요약·세 항목이 모두 비어 있지 않고 용어는 "AI 피드백"으로 통일돼 있다.
  - 창 초과 시 실패가 아닌 안내가 뜨고 재진입하면 GET부터 다시 시작한다.
- **확인 방법**:
  - 스크린샷(시트, 분석중, 결과).
  - 앱 로그의 GET 간격과 POST 횟수(1회).
  - 사용자가 알려 준 토큰으로 `GET /posts/{id}/ai-review`를 조회해 `status`·`completedAt`을 확인한다(토큰 비출력).
  - 소요 시간(POST~완료)을 기록한다.
- **되돌릴 수 없음 여부**: **되돌릴 수 없음.** 게시물당 AI 리뷰 요청은 최대 3회이고 이 시나리오가 1회를 쓴다. 완료된 리뷰는 다시 만들 수 없으며 외부 OpenAI 호출 비용이 발생한다. 실행 전 사용자 확인을 받는다.
- **플랫폼 차이**:
  - Web: 푸시가 없으므로 알림함 확인은 새로고침으로 한다(open-questions Q-04).
  - iOS 시뮬레이터에서는 완료 푸시 도착을 확인하지 못할 수 있다(AG-AIR-002에서 실기기로 확인).

### AG-AIR-002 분석 중 백그라운드 복귀와 실제 푸시 탭

- **대응 TC**: TC-AIR-061
- **사전 조건**:
  - AG-AIR-001에서 보낸 요청이 아직 PROCESSING이다(추가 요청을 쓰지 않도록 같은 요청을 이어서 쓴다). 완료가 너무 빠르면 이 시나리오는 보류한다.
  - 실기기 또는 푸시를 받을 수 있는 환경(FCM 토큰이 서버에 등록돼 있고 알림 권한이 허용됨). 푸시 수신 설정 `aiReviewPushEnabled`가 켜져 있다.
- **단계**:
  1. 분석 중 화면에서 앱을 백그라운드로 보내고 30초 이상 둔다.
  2. 앱을 다시 열어 화면이 PROCESSING 또는 완료로 올바르게 갱신되고 GET이 즉시 한 번 나가는지 본다(앱 로그).
  3. 앱을 홈 화면이 아닌 곳에 둔 상태(백그라운드)에서 완료 푸시가 도착하는지 본다.
  4. 푸시를 탭해 게시물 상세로 이동하고 결과 시트가 자동으로 한 번 열리는지 본다.
  5. 시트를 닫고 뒤로 갔다가 같은 게시물에 다시 들어가 시트가 다시 자동으로 열리지 않는지 확인한다.
- **기대 결과**(관찰 가능한 것):
  - 복귀 시 폴링이 GET부터 새 창으로 재개된다.
  - 푸시 탭 후 게시물 상세와 결과(또는 실패) 시트가 한 번만 열린다.
  - 푸시를 탭하면 알림 읽음 처리가 되어 미읽음 점이 사라진다.
- **확인 방법**:
  - 스크린샷, 화면 녹화, 푸시 알림 센터 캡처.
  - 앱 로그의 `PATCH /notifications/{id}/read` 호출과 GET 재개 시각.
- **되돌릴 수 없음 여부**: AG-AIR-001의 요청을 이어서 쓰므로 추가로 되돌릴 수 없는 것은 없다(푸시 수신과 읽음 처리는 서버에 기록된다).
- **플랫폼 차이**:
  - Web은 푸시가 없어 생략한다.
  - iOS 시뮬레이터는 FCM/APNs 실제 도착이 제한적이라 실기기를 쓴다.
  - Android 13 이상은 알림 권한 다이얼로그가 먼저 뜬다.
