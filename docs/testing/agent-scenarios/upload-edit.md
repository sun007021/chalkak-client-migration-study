# 에이전트 시나리오: 업로드·편집(UPL, EDIT)

실제 카메라·앨범, S3와 서버 처리, 편집 시각 품질과 제스처 감각처럼 자동화할 수 없는 항목이다. 대응 TC는 [catalog/upload-edit.md](../catalog/upload-edit.md)이다. 업로드 시나리오는 게시물을 만들면 주제당 1장 슬롯을 쓰므로 실행 순서와 횟수를 사용자와 정하고 진행한다.
공통 규칙(모든 시나리오): 서버는 개발 서버 `https://chalkak-dev.pysun.kr/api/v1/`이다. 테스트 계정은 **실행 시 사용자에게 받은 카카오 계정**을 쓰며 문서·로그·스크린샷 파일명·커밋에 계정 정보와 토큰을 적지 않는다. 서버 API 조회가 필요하면 앱 디버그 로그나 사용자가 알려 준 값을 환경변수(`CHALKAK_ACCESS_TOKEN` 등)로만 다루고 출력에 남기지 않는다. 클라우드 컨테이너의 `curl`은 프록시 때문에 개발 서버에 닿지 않으므로(strategy §6) 사용자 Mac의 시뮬레이터·에뮬레이터와 Mac 터미널에서 실행한다. 스크린샷은 `agent-runs/<날짜>/<플랫폼>/AG-<영역>-NNN-<단계>.png`처럼 저장하고 계정 정보가 보이면 가린다. 결과는 패리티 매트릭스의 `A✓`로 기록한다. 플랫폼은 iOS, Android, Flutter(iOS·Android), React Native(iOS·Android), Web 순서로 같은 시나리오를 수행하고, 아래 "플랫폼 차이"에 적은 곳만 단계가 다르다.

### AG-UPL-001 앨범 사진 업로드 → 성공 → 서버 처리 확인

- **대응 TC**: TC-UPL-091
- **사전 조건**:
  - 오늘 OPEN 주제가 있고 내 계정은 이 주제에 아직 게시물이 없다(`GET /posts/today`의 `isPosted=false`).
  - 기기 앨범에 테스트 사진이 있다. 개인정보가 없는 풍경·사물 사진(얼굴·위치 정보가 들어 있지 않은 것)을 쓴다. iOS 시뮬레이터는 `xcrun simctl addmedia booted <파일>`, Android 에뮬레이터는 `adb push` 후 미디어 스캔, Web은 파일 선택기에서 고른다.
  - 관리자 승인은 사람이 해야 하므로 이 시나리오는 PENDING까지만 확인한다.
- **단계**:
  1. 홈 히어로 또는 하단 + 버튼으로 업로드를 연다. 게이트를 통과해 업로드 화면이 열리는지 본다.
  2. 앨범에서 사진을 고르고 편집 화면에서 아무것도 바꾸지 않고 "완료"를 누른다.
  3. 제목에 "테스트"를 입력한다(선택 사항).
  4. "전시하기"를 누르고 성공 화면의 문구("‘{주제}’을/를 기록했어요."와 상태 문구)를 스크린샷으로 남긴다.
  5. "확인했어요."를 눌러 전시가 업로드한 날짜로 열리는지 본다.
  6. 10초 간격으로 최대 2분 동안 `GET /posts/today`를 조회해 `moderationStatus`가 VALIDATING에서 PENDING으로 바뀌는지 기록한다.
  7. 홈으로 이동해 히어로가 "검수 대기" 배지 사진으로 바뀌었는지 본다.
  8. 업로드 버튼을 다시 눌러 "이미 이 주제에 게시물을 작성했어요."가 뜨고 화면이 열리지 않는지 확인한다.
- **기대 결과**(관찰 가능한 것):
  - 성공 화면의 조사(을/를)와 상태 문구가 맞다(PENDING이면 "검수를 기다리고 있어요…", VALIDATING이면 "사진을 확인하고 있어요…").
  - 서버 상태가 VALIDATING → PENDING으로 넘어가고 REJECTED로 가지 않는다.
  - 재진입 시 중복 작성이 막힌다.
- **확인 방법**:
  - 앱 로그에서 정책 발급(`POST /posts/uploads`), S3 PUT, `POST /posts` 순서와 응답 코드를 확인한다(토큰·presigned URL 서명 부분은 기록하지 않는다).
  - 사용자가 알려 준 토큰으로 `GET /posts/today`를 반복 조회한 결과 표(시각, 상태).
  - 스크린샷(성공 화면, 홈 히어로).
- **되돌릴 수 없음 여부**: **되돌릴 수 없음.** 주제당 1장이라 오늘 슬롯을 사용한다. PENDING이 된 뒤 앱에서 삭제(AG-FEED-002)하면 슬롯은 회복되지만 서버에 논리 삭제 기록과 업로드 행이 남고, VALIDATING 중에는 삭제할 수 없다. 처리 실패(REJECTED)가 되면 같은 주제로 다시 제출할 수 있다. 실행 전 사용자에게 오늘 슬롯을 써도 되는지 확인한다.
- **플랫폼 차이**:
  - iOS 시뮬레이터: 시스템 사진 선택기가 시뮬레이터 앨범을 보여 준다. 카메라는 사용할 수 없다.
  - Web: 데스크톱 브라우저는 카메라 버튼이 숨겨지고 파일 선택기만 있다.
  - Flutter·RN은 iOS·Android 각각 한 번씩 수행하되 서버 슬롯 문제로 같은 날에는 한 플랫폼만 제출하고 나머지는 "전시하기" 직전까지 확인한다.

### AG-UPL-002 카메라 촬영과 권한 다이얼로그

- **대응 TC**: TC-UPL-022
- **사전 조건**:
  - Android 에뮬레이터는 가상 카메라(Virtual Scene 또는 Webcam)를 켠다. iOS 시뮬레이터는 카메라가 없으므로 실기기가 있으면 실기기를 쓴다.
  - 권한 상태를 초기화한다: iOS `xcrun simctl privacy booted reset all`(실기기는 앱 삭제 후 재설치), Android `adb shell pm reset-permissions` 또는 앱 데이터 삭제.
  - **전시하기 직전에서 멈춘다**(제출하면 슬롯을 쓴다).
- **단계**:
  1. 업로드 화면을 열고 카메라 버튼을 확인한다. iOS 시뮬레이터에서는 카메라 버튼이 숨겨져 있어야 하고 이 경우 앨범 선택으로 이어서 4번부터 수행한다.
  2. 카메라 버튼을 눌러 OS 권한 다이얼로그(카메라, 사진 추가/저장)가 뜨면 먼저 "거부"를 선택한다. 앱이 멈추지 않고 안내(설정 이동 또는 저장 없이 촬영 등)가 나오는지 본다.
  3. 권한을 허용으로 바꾸고 다시 촬영한다. 촬영본이 기기 앨범에 저장되는지(Android `Pictures/Chalkak/chalkak-photo-*.jpg`) 확인한다.
  4. 저장 권한을 거부한 상태에서 촬영해 토스트 "사진을 갤러리에 저장하지 못했어요."가 뜨고 선택한 사진은 유지되는지 본다.
  5. 편집 화면에서 완료하고 "전시하기" 버튼이 활성화되는지만 확인한 뒤 화면을 닫는다(제출하지 않는다).
  6. 화면을 닫고 서버에 게시물이 생기지 않았는지 `GET /posts/today`로 확인한다.
- **기대 결과**(관찰 가능한 것):
  - 권한을 거부해도 앱이 멈추지 않고 앨범 선택으로 계속할 수 있다.
  - 촬영본은 앨범에 한 번만 저장된다. 저장 실패는 토스트만 뜨고 업로드 준비는 계속된다.
  - 서버에는 게시물이 생기지 않는다(정책 발급 행은 남을 수 있다).
- **확인 방법**:
  - 스크린샷(권한 다이얼로그, 토스트, 앨범 확인).
  - `adb shell ls /sdcard/Pictures/Chalkak/` 또는 사진 앱에서 파일 확인.
  - `GET /posts/today`의 `isPosted=false`.
- **되돌릴 수 없음 여부**: 촬영본이 기기 앨범에 남는다(기기 데이터이며 서버에는 영향 없음). 정책 발급 호출로 서버에 미사용 업로드 행이 생길 수 있고 삭제 API는 없다. 게시물은 만들지 않는다.
- **플랫폼 차이**:
  - Android API 28 이하 에뮬레이터에서는 저장소 쓰기 권한 다이얼로그가 추가로 뜬다. API 29 이상에서는 뜨지 않는다.
  - iOS는 카메라 전에 사진 추가 전용 권한을 먼저 요청한다.
  - Web은 이 시나리오를 생략한다(카메라 버튼 없음).

### AG-UPL-003 고해상도·대용량 사진의 실제 인코딩과 서버 수용

- **대응 TC**: TC-UPL-092
- **사전 조건**:
  - 12MP 이상(가능하면 원본 5 MiB 이상, 노이즈가 많은 야간 사진) JPEG를 기기 앨범에 둔다. 개인정보가 없는 풍경·사물 사진(얼굴·위치 정보가 들어 있지 않은 것)을 쓴다.
  - 오늘 슬롯이 비어 있다. AG-UPL-001을 같은 날 수행했다면 그 게시물을 PENDING 이후 삭제해 슬롯을 비우거나 이 시나리오는 다른 날 수행한다.
- **단계**:
  1. 업로드 화면에서 해당 사진을 고르고 편집 "완료"를 누른다. 완료 시각을 기록한다.
  2. "전시하기" 활성화까지(앱 로그의 "준비 완료") 걸린 시간과 앱이 느려지거나 종료되지 않는지 본다.
  3. 앱 로그에서 정책 `maxBytes`, 최종 WebP 바이트, 출력 해상도, 시도한 품질을 확인한다.
  4. "전시하기"로 제출하고 성공 화면까지 확인한다.
  5. `GET /posts/today`를 10초 간격으로 최대 3분 조회해 VALIDATING → PENDING으로 가는지, REJECTED(`isPosted=false`로 되돌아옴)가 되지 않는지 확인한다.
- **기대 결과**(관찰 가능한 것):
  - 인코딩이 몇 초~수십 초 안에 끝나고 앱이 메모리 부족으로 종료되지 않는다.
  - 최종 파일 크기가 정책 `maxBytes`(5,242,880) 이하이고 긴 변이 4096 이하이다.
  - 서버가 PENDING까지 정상 처리하고 `TOO_LARGE`·`CORRUPTED_IMAGE`로 거절하지 않는다.
- **확인 방법**:
  - 앱 디버그 로그의 인코딩 결과(바이트·해상도·품질·소요 ms).
  - `GET /posts/today` 조회 결과 표.
  - 스크린샷(성공 화면).
- **되돌릴 수 없음 여부**: **되돌릴 수 없음.** AG-UPL-001과 같다(주제당 1장, 삭제 시 슬롯 회복, 서버에 논리 삭제 기록 잔존).
- **플랫폼 차이**:
  - 저사양 기기·에뮬레이터에서는 인코딩 시간이 더 걸린다. 시간은 SLA가 아니라 비교 참고용으로만 기록한다.
  - Web은 브라우저 메모리 한계를 함께 본다(탭이 죽지 않는지).
  - iOS는 HEIC 원본도 한 번 시도한다.

### AG-EDIT-001 필터 6종의 시각 품질

- **대응 TC**: TC-EDIT-049
- **사전 조건**:
  - 참조 사진 3장(밝은 풍경, 저조도, 다채로운 색)을 기기 앨범에 둔다. 얼굴이 나오는 사진은 쓰지 않는다.
  - 제출하지 않는다(편집 후 취소하거나 "전시하기" 전에 닫는다).
- **단계**:
  1. 업로드 화면에서 참조 사진 하나를 고르고 편집 화면의 필터 탭을 연다.
  2. 원본, 흑백, 따뜻하게, 차갑게, 빈티지, 선명하게를 차례로 선택하며 각각 스크린샷을 남긴다.
  3. 나머지 두 사진에서도 반복한다.
  4. 필터를 고른 상태에서 "완료" 후 업로드 화면의 미리보기가 편집 화면의 결과와 같은지 본다.
- **기대 결과**(관찰 가능한 것):
  - 흑백은 완전한 무채색, 따뜻하게는 붉고 노란 쪽, 차갑게는 푸른 쪽으로 보이고 빈티지·선명하게는 의도한 분위기다.
  - 색 띠(banding), 하이라이트 날림, 노이즈 증폭 같은 눈에 띄는 열화가 없다.
  - 편집 화면 미리보기와 완료 후 결과가 같다.
- **확인 방법**:
  - 필터×사진 스크린샷 격자(3×6).
  - 골든 기대값과 다른 점이 보이면 TC-EDIT 골든 테스트가 놓친 경로를 기록한다.
- **되돌릴 수 없음 여부**: 해당 없음(제출하지 않는다).
- **플랫폼 차이**:
  - 플랫폼마다 미리보기 해상도가 달라 약간의 차이는 허용한다. 판단 기준은 TC-EDIT-048(평균 ΔE ≤ 3)이다.

### AG-EDIT-002 자르기·회전 제스처 감각

- **대응 TC**: TC-EDIT-050
- **사전 조건**:
  - 가로·세로·정사각 사진 각 1장.
  - 실기기 권장(시뮬레이터는 마우스 드래그).
- **단계**:
  1. 자르기 탭에서 비율을 원본, 자유, 1:1, 4:5, 5:4, 3:4, 4:3, 9:16, 16:9 순으로 선택하며 프레임이 즉시 새 비율로 시작하는지 본다.
  2. 프레임의 모서리·변 핸들을 끌어 크기를 바꾸고, 프레임 안쪽을 끌어 이동하며, 사진을 핀치로 확대·이동한다.
  3. 프레임이 이미지 밖으로 나가려 할 때와 최소 크기 근처에서의 동작을 본다.
  4. "90도 회전"을 4번 누르며 고정 비율이 함께 돌아가는지 본다.
  5. "초기화"를 눌러 처음 상태로 돌아가는지 본다.
  6. 자르기를 마친 뒤 조정·필터 탭으로 가서 잘린 사진에 적용되는지 본다.
- **기대 결과**(관찰 가능한 것):
  - 손가락 추종이 부드럽고 프레임이 튀거나 한계에서 떨리지 않는다.
  - 비율 변경과 회전 후 프레임이 사진 안에 적절히 놓인다.
- **확인 방법**:
  - 화면 녹화와 비율별 스크린샷.
- **되돌릴 수 없음 여부**: 해당 없음.
- **플랫폼 차이**:
  - Web은 마우스 드래그로 같은 동작을 수행하고 터치 환경(모바일 브라우저)에서도 한 번 확인한다.

### AG-EDIT-003 조정 눈금자의 디텐트·햅틱·관성

- **대응 TC**: TC-EDIT-051
- **사전 조건**:
  - 실기기(햅틱 확인용)가 필요하다. 시뮬레이터에서는 디텐트 위치만 시각으로 확인한다.
  - 저조도 사진 1장.
- **단계**:
  1. 조정 탭에서 노출 눈금자를 천천히 좌우로 끌어 0 위치에서 멈칫하는지 본다.
  2. "자동"을 켜서 자동 보정 값이 채워진 뒤 항목 눈금자의 자동 몫 위치(점)에서 멈칫하는지 본다.
  3. 빠르게 던졌을 때(관성)의 감속이 자연스러운지 본다.
  4. 항목을 바꿔 대비, 하이라이트, 그림자, 블랙 포인트, 채도, 따뜻함에서도 반복한다.
  5. 자동 몫 위치로 되돌려 직접 만진 표시가 사라지는지 본다.
- **기대 결과**(관찰 가능한 것):
  - 디텐트에서 햅틱이 한 번 느껴지고 과하게 반복되지 않는다.
  - 관성이 자연스럽고 값 표시(×100)가 눈금자와 일치한다.
- **확인 방법**:
  - 화면 녹화, 값 표시 스크린샷. 햅틱은 관찰자가 서술로 기록한다.
- **되돌릴 수 없음 여부**: 해당 없음.
- **플랫폼 차이**:
  - Web·데스크톱에는 햅틱이 없어 디텐트의 시각적 멈춤만 본다.

### AG-EDIT-004 플랫폼 간 편집 결과 비교(ΔE)

- **대응 TC**: TC-EDIT-048
- **사전 조건**:
  - 다섯 플랫폼 구현이 끝난 마무리 단계에서 수행한다.
  - 기준 입력 사진과 편집값 표는 `shared/photo-edit/golden/`의 기준 이미지 세트를 쓴다.
  - Mac에서 평균 ΔE를 계산하는 스크립트(`shared/scripts/`에 둘 도구)를 쓴다.
- **단계**:
  1. 각 플랫폼에서 같은 기준 사진을 열고 필터(6종 각각)와 대표 조정값(노출 +0.5, 채도 -0.5, 따뜻함 +0.5)을 UI로 적용한다.
  2. 편집 화면 미리보기를 같은 크기(긴 변 1080px)로 스크린샷 저장한다.
  3. 스크립트로 플랫폼별 스크린샷과 기준 이미지의 평균 ΔE를 계산한다.

- **기대 결과**(관찰 가능한 것):
  - 모든 조합에서 평균 ΔE ≤ 3이다.

- **확인 방법**:
  - 스크립트 출력 표(조합 × 플랫폼 ΔE)와 기준·결과 이미지 쌍.
- **되돌릴 수 없음 여부**: 해당 없음(제출하지 않는다).
- **플랫폼 차이**:
  - Web은 브라우저 색 관리(디스플레이 프로파일)에 따라 스크린샷 값이 달라질 수 있어 sRGB로 고정한 창에서 캡처한다.
