# 에이전트 시나리오: BOOT, AUTH (그리고 NET의 A 항목)

[catalog/boot-auth.md](../catalog/boot-auth.md)와 [catalog/common-infra.md](../catalog/common-infra.md)에서 구분이 `A`인 TC를 서브에이전트가 시뮬레이터·에뮬레이터·브라우저와 개발 서버에서 직접 확인하는 절차다. 자동화로 닫을 수 있는 것은 여기에 두지 않았다([strategy.md §1](../strategy.md#무엇을-a로-미루나)).

## 공통 전제 (이 문서의 모든 시나리오)

- 개발 서버: `https://chalkak-dev.pysun.kr/api/v1/`. 클라우드 컨테이너의 `curl`은 프록시 때문에 닿지 않으므로 **사용자 Mac의 시뮬레이터·에뮬레이터·브라우저**에서 실행한다([strategy.md §6](../strategy.md#6-개발-서버-e2e마지막-단계)).
- 테스트 카카오 계정: **실행 시 사용자에게 받은 계정**을 쓴다. 이 문서·로그·스크린샷 파일명·커밋 어디에도 계정 값, 토큰, 키를 적지 않는다. 스크린샷에 계정 이메일이나 토큰이 보이면 가리고 저장한다.
- 앱은 5개 플랫폼 각각의 개발 빌드(`API_BASE_URL`이 개발 서버)다. 카카오 개발자 콘솔 식별자는 [Q-15](../../spec/open-questions.md)에 따라 기존 앱과 같은 번들 ID·패키지명을 쓴다.
- 서버 상태 확인은 앱 화면, 디버그 빌드의 네트워크 로그(토큰은 마스킹), 그리고 필요할 때만 사용자에게 받은 토큰으로 하는 읽기 전용 API 조회로 한다. 토큰은 환경변수로만 받고 파일에 쓰지 않는다.
- 각 시나리오의 "되돌릴 수 없음"이 예이면 실행 전에 사용자에게 한 줄로 알리고, 탈퇴처럼 계정이 사라지는 것은 **사용자의 명시 확인 없이는 실행하지 않는다.**
- 결과는 플랫폼별로 통과/실패/차이를 기록해 [parity-matrix.md](../parity-matrix.md)의 `A✓` 칸에 반영한다.

## BOOT

### AG-BOOT-001 iTunes lookup 실제 조회 (iOS 계열 한정)

- 대응 TC: TC-BOOT-038
- 사전 조건: iOS 시뮬레이터(iOS native, Flutter iOS, RN iOS). 스토어 조회 설정을 **켠** 디버그 빌드. 시뮬레이터는 인터넷에 연결됨. 계정 상태와 서버 데이터는 무관(로그인 불필요).
- 단계:
  1. 앱을 삭제 후 설치하고 시작한다.
  2. 시작 직후 버전 게이트가 조회를 수행하도록 두고 5초 기다린다.
  3. 앱 번들 버전을 스토어에 존재하는 현재 버전보다 낮게(예: 0.1.0), 같게, 높게 바꾼 빌드를 차례로 만들어 1~2를 반복한다. 번들 버전만 바꿔 빌드한다.
  4. 네트워크를 끊은 시뮬레이터(호스트 Wi-Fi 끄기)에서 한 번 더 시작한다.
- 기대 결과: 낮은 버전(major 또는 minor가 낮음)은 닫을 수 없는 "업데이트가 필요해요" 다이얼로그. patch만 낮거나 같거나 높은 버전은 홈 또는 로그인 화면으로 통과. 네트워크 단절은 통과(앱을 막지 않음). 어느 경우에도 크래시 없음.
- 확인 방법: 스크린샷 비교(다이얼로그 문구 3종과 버튼 1개, 바깥 탭으로 안 닫힘), 디버그 로그에서 lookup URL에 bundleId·국가 코드·entity=software가 있는지와 파싱된 스토어 버전.
- 되돌릴 수 없음: 아니오(읽기 전용 외부 조회).
- 플랫폼 차이: iOS 시뮬레이터에서만 수행. Android 계열은 Play In-App Update라 스토어에 올리지 않는 이 레포에서는 실조회 시나리오가 없다(TC-BOOT-030의 Fake로 대체). Web은 게이트 없음.

### AG-BOOT-002 콜드 스타트 스플래시 전환의 시각 품질

- 대응 TC: TC-BOOT-039
- 사전 조건: 각 플랫폼 개발 빌드. (a) 인증 세션이 있는 상태 (b) 게스트 상태 (c) 세션 없음 상태를 각각 만들 수 있어야 한다. 개발 서버 정상, 홈 공개 데이터 로드 가능.
- 단계:
  1. 앱을 강제 종료한 뒤 (a) 상태로 콜드 스타트하고 시작 직후부터 홈이 보일 때까지 0.2초 간격으로 화면을 캡처한다(총 3초 이상).
  2. (b), (c) 상태로 같은 절차를 반복한다.
  3. 네트워크 속도를 낮춘 환경(느린 3G 프로필 또는 개발자 옵션)에서 (a)를 한 번 더 수행한다.
- 기대 결과: 스플래시 → 홈(또는 로그인)으로 전환될 때 빈 화면 번쩍임, 로그인 화면이 잠깐 비쳤다 사라짐, 레이아웃 점프가 없다. 느린 망에서도 스플래시는 약 700ms를 넘기지 않고 홈이 로딩 상태로 열린다.
- 확인 방법: 캡처 시퀀스를 눈으로 검토하고 이상 프레임 번호를 기록한다. 스플래시 해제 시각은 디버그 로그의 타임스탬프로 확인한다.
- 되돌릴 수 없음: 아니오.
- 플랫폼 차이: iOS 시뮬레이터(런치 스크린), Android 에뮬레이터(시스템 스플래시 API), Web 브라우저(초기 로딩 화면). Web은 강제 종료 대신 새 탭 로드로 대체한다.

## AUTH

### AG-AUTH-001 실제 카카오 로그인 성공 (톡 앱과 카카오계정 폴백)

- 대응 TC: TC-AUTH-061
- 사전 조건: 기기 상태는 앱 신규 설치(세션 없음). 계정 상태는 **실행 시 사용자에게 받은 카카오 계정**이며 이미 가입된 회원이어야 한다(미가입 계정은 AG-ONB-001). 카카오톡 앱 설치 여부를 두 경우로 나눈다. 시뮬레이터·에뮬레이터는 카카오톡 앱이 없는 것이 기본이므로 "카카오계정 로그인 폴백" 경로를 확인한다. 톡 앱 경로는 실기기가 있을 때만 수행하고 없으면 건너뛴다고 기록한다. 개발 서버 정상.
- 단계:
  1. 로그인 화면에서 "카카오로 계속하기"를 탭한다.
  2. 카카오 로그인 화면(웹뷰 또는 브라우저)에서 사용자에게 받은 계정으로 로그인한다. 계정 값은 에이전트가 환경에서 읽어 입력하며 기록하지 않는다.
  3. 동의 화면이 나오면 진행한다.
  4. 앱으로 돌아와 홈이 열릴 때까지 기다린다.
  5. 앱을 강제 종료하고 다시 시작해 로그인 화면 없이 홈이 열리는지 확인한다.
  6. 설정 탭의 사인 카드와 푸시 알림 토글이 서버 값으로 채워지는지 확인한다(인증이 실제로 동작하는 증거).
- 기대 결과: 로그인 화면 → 카카오 → 홈. 재시작 후에도 홈 유지. 설정 탭의 사인 카드·토글이 로드됨. 오류 알림 없음.
- 확인 방법: 스크린샷(로그인 전·후 홈, 설정 탭), 디버그 로그에서 POST /auth/social-login이 200 LOGIN_SUCCESS인지(토큰 마스킹), 그 직후 PUT /push-devices/current가 시도됐는지.
- 되돌릴 수 없음: 아니오(로그인 세션만 생성). 단 서버에 로그인 세션 이력이 남는다.
- 플랫폼 차이: iOS 시뮬레이터(SFSafariViewController 또는 ASWebAuthenticationSession 계열 카카오 웹 로그인), Android 에뮬레이터(Custom Tab 계열), 웹 브라우저는 AG-AUTH-005. Flutter·RN은 각 네이티브 브리지를 통과하는지 확인한다.

### AG-AUTH-002 카카오 로그인 중 사용자 취소

- 대응 TC: TC-AUTH-062
- 사전 조건: AG-AUTH-001과 같다(앱 신규 설치, 세션 없음). 로그인 계정은 입력하지 않는다.
- 단계:
  1. "카카오로 계속하기"를 탭해 카카오 로그인 화면을 연다.
  2. 로그인하지 않고 닫기/뒤로가기/취소한다(카카오 화면 상단 닫기, iOS의 취소, Android 뒤로가기).
  3. 앱 화면으로 돌아온 직후 상태를 본다.
  4. "카카오로 계속하기"를 다시 탭해 카카오 화면이 다시 열리는지 확인한다.
  5. 이번에는 "로그인 없이 사진 둘러보기"를 탭해 홈이 게스트로 열리는지 확인한다.
- 기대 결과: 취소 후 오류 알림이나 토스트가 없고 로그인 화면이 그대로이며 버튼이 다시 눌린다. 카카오톡 앱 로그인에서 취소했을 때는 계정 로그인으로 폴백하지 않는다(톡 앱 실기기가 있을 때만 확인). 게스트 진입도 정상.
- 확인 방법: 취소 직후 스크린샷, 디버그 로그에서 POST /auth/social-login 호출이 0건인지.
- 되돌릴 수 없음: 아니오.
- 플랫폼 차이: iOS 시뮬레이터와 Android 에뮬레이터는 취소 제스처가 다르다(iOS는 시트의 취소, Android는 뒤로가기). 웹은 팝업 닫기.

### AG-AUTH-003 로그아웃 후 서버 세션 폐기 확인

- 대응 TC: TC-AUTH-063
- 사전 조건: AG-AUTH-001로 로그인된 상태. 디버그 빌드가 로그아웃 직전에 현재 refresh token을 **메모리 내에서만** 보관해 에이전트가 한 번 쓸 수 있는 디버그 훅을 제공하거나, 사용자가 임시 토큰 조회를 승인한다. 이 값은 파일·로그에 쓰지 않는다. 개발 서버 정상.
- 단계:
  1. 로그아웃 직전 현재 refresh token을 디버그 훅으로 환경변수 하나에만 담는다.
  2. 설정 탭에서 "로그아웃" → 확인 다이얼로그에서 확인한다.
  3. 로그인 화면이 열리는지 확인한다.
  4. `POST /auth/refresh {refreshToken}`을 환경변수 값으로 한 번 보낸다(시뮬레이터가 아닌 사용자 Mac에서).
  5. 앱을 종료하고 다시 시작해 로그인 화면이 열리는지 확인한다.
  6. 환경변수를 비운다.
- 기대 결과: 로그아웃 후 로그인 화면. refresh 호출은 401 REAUTHENTICATION_REQUIRED("다시 로그인해 주세요."). 재시작해도 로그인 화면.
- 확인 방법: 로그인 화면 스크린샷, 4단계 응답 상태 코드와 errorCode(토큰 값은 적지 않음), 디버그 로그에서 POST /auth/logout이 호출되고 푸시 기기 해제 API 호출은 없는지.
- 되돌릴 수 없음: 예(서버 세션이 폐기됨. 같은 세션으로 다시 쓸 수 없으며 다시 로그인하면 된다).
- 플랫폼 차이: iOS 시뮬레이터, Android 에뮬레이터, 웹 브라우저(웹은 IndexedDB 임시 보관 구현이라 refresh 보관소가 비워졌는지 개발자 도구에서도 확인).

### AG-AUTH-004 회원탈퇴 (사용자 확인 필수)

- 대응 TC: TC-AUTH-064
- 사전 조건: **이 시나리오는 사용자의 명시적 확인 없이 실행하지 않는다.** 실행 직전 "이 계정이 개발 서버에서 탈퇴됩니다"라고 알리고 확인을 받는다. 탈퇴해도 되는 전용 테스트 계정(실행 시 사용자에게 받은 계정)이어야 하며, 가입 흐름 검증(AG-ONB-001)과 한 번에 묶어 새로 만든 계정을 정리하는 용도로 쓰는 것이 안전하다. 로그인된 상태. 개발 서버 정상.
- 단계:
  1. 설정 탭에서 "회원탈퇴"를 탭한다. 다이얼로그 "정말 회원탈퇴 하시겠습니까?"를 확인한다.
  2. 먼저 "취소"를 눌러 아무 변화가 없는지 확인한다.
  3. 사용자 확인을 받은 뒤 다시 "회원탈퇴" → 확인을 누른다.
  4. 로그인 화면이 열리는지 확인한다.
  5. 앱을 재시작해 로그인 화면이 유지되는지 확인한다.
  6. 같은 카카오 계정으로 다시 로그인을 시도해 신규 가입 흐름(약관)이 나오는지 확인한다. 가입은 진행하지 않고 뒤로 간다.
- 기대 결과: 취소는 무변화. 확인 시 DELETE /users/me가 204이고 로그인 화면이 열린다. 재시작 후에도 로그인 화면. 같은 계정으로 로그인하면 SIGN_UP_REQUIRED(새 회원)로 약관 화면이 열린다. 카카오 연결 해제 호출은 없다.
- 확인 방법: 각 단계 스크린샷, 디버그 로그에서 DELETE /users/me 상태 204, 직후 보호된 API가 401이 되는 것(앱이 이미 로그인 화면이라 호출이 없으면 로그만 확인).
- 되돌릴 수 없음: 예(회원 논리 삭제, 모든 세션과 푸시 기기 삭제. 같은 소셜 계정은 새 회원으로 재가입만 가능).
- 플랫폼 차이: 플랫폼마다 한 번씩 수행하지 않는다. 같은 계정을 쓰므로 플랫폼별로 계정을 다시 가입한 뒤 탈퇴하거나, 사용자와 합의한 대표 플랫폼 1~2곳에서만 수행하고 나머지는 자동 TC(TC-AUTH-043~049)로 갈음한다고 기록한다.

### AG-AUTH-005 Web 카카오 로그인 (Q-02 결론 이후)

- 대응 TC: TC-AUTH-065
- 사전 조건: Web 개발 빌드, Q-02(카카오 JS SDK에서 OIDC idToken과 nonce를 받는지, 리다이렉트 방식에서 rawNonce 보관 위치)가 결정된 상태. 데스크톱 브라우저. 계정은 실행 시 사용자에게 받은 카카오 계정. 개발 서버 정상, 개발 서버에서 웹 오리진이 CORS 허용(AG-NET-002 선행).
- 단계:
  1. 세션 없는 브라우저 프로필(시크릿 창)에서 앱을 연다.
  2. "카카오로 계속하기"를 눌러 카카오 웹 로그인 흐름을 끝까지 수행한다.
  3. 앱으로 돌아온 뒤 홈이 열리는지, 새로고침해도 세션이 유지되는지 확인한다.
  4. 개발자 도구 Application 탭에서 access token이 메모리, refresh token 보관소가 임시안(IndexedDB)에만 있고 localStorage에 토큰이 없는지 확인한다.
  5. 로그아웃해 보관소가 비워지는지 확인한다.
- 기대 결과: 로그인 성공, 새로고침 뒤 세션 유지, localStorage에 토큰 없음, 로그아웃 시 보관소 비움.
- 확인 방법: 스크린샷, 네트워크 탭에서 POST /auth/social-login 요청 바디의 필드 이름(값은 가림)과 응답 상태, Application 탭 스크린샷(값 가림).
- 되돌릴 수 없음: 아니오(로그인 세션만).
- 플랫폼 차이: Web 한정. 막히면 open-questions Q-02의 임시안(개발용 로그인 우회, 게스트)으로 나머지를 진행하고 이 시나리오는 "차단"으로 기록한다.

## 공통 인프라(NET)

### AG-NET-001 실제 네트워크 단절·복구

- 대응 TC: TC-NET-061
- 사전 조건: 인증 세션이 있는 개발 빌드(AG-AUTH-001 이후). 시뮬레이터는 호스트 네트워크에 연결되어 있고, 호스트에서 Wi-Fi를 끄거나 네트워크 링크 컨디셔너(iOS) / 에뮬레이터 네트워크 설정(Android)으로 단절을 만들 수 있어야 한다. 웹은 브라우저 개발자 도구의 Offline.
- 단계:
  1. 홈이 열린 상태에서 네트워크를 끊고 홈을 당겨서 새로고침한다.
  2. 전시 탭으로 이동해 목록을 연다(처음 열어 콘텐츠가 없는 경우를 만들기 위해 앱 재시작 후 수행).
  3. 설정 탭에서 푸시 알림 토글 하나를 바꾼다.
  4. 피드백 화면에서 내용을 입력하고 "보내기"를 누른다.
  5. 네트워크를 복구한다. 각 화면에서 "다시 시도"를 누르거나 다시 새로고침한다.
  6. 네트워크를 끊은 채 앱을 포그라운드/백그라운드로 전환해 본다.
  7. 요청을 보낸 직후(응답 전) 네트워크를 끊어 본다(피드백 전송 직후).
- 기대 결과: 콘텐츠가 이미 있는 화면은 콘텐츠를 유지하고 "네트워크 연결을 확인해 주세요." 토스트. 콘텐츠가 없는 화면은 오류 화면과 "다시 시도". 설정 토글은 이전 값으로 돌아오고 토스트. 피드백은 입력이 유지되고 다시 보낼 수 있다. 복구 뒤 모두 정상 동작. 앱이 멈추거나 무한 로딩이 되지 않는다.
- 확인 방법: 단계별 스크린샷, 디버그 로그에서 요청 타임아웃(연결 10초·응답 15초 상한)과 멱등 요청의 재시도 횟수(최대 2회), POST 재시도 0회.
- 되돌릴 수 없음: 7단계에서 서버에 피드백이 도달했을 수 있으면 피드백 1건이 남는다(삭제 불가). 그 외는 아니오.
- 플랫폼 차이: iOS 시뮬레이터는 Network Link Conditioner 또는 호스트 Wi-Fi, Android 에뮬레이터는 확장 컨트롤의 네트워크 또는 airplane mode, 웹은 Offline 토글(플랫폼 차이로 예외 타입이 다르다는 점도 확인).

### AG-NET-002 배포 웹 CORS

- 대응 TC: TC-NET-062
- 사전 조건: Web을 로컬 프록시 없이 실제 오리진(배포 후보 도메인 또는 로컬 정적 서버의 localhost 포트)에서 연다. 데스크톱 브라우저. 로그인 불필요.
- 단계:
  1. 개발 서버 주소를 직접 base URL로 하는 빌드로 페이지를 연다(Vite dev proxy 미사용).
  2. 비로그인 공개 API(GET /topics, GET /posts, GET /banners)가 화면에서 호출되게 한다.
  3. 개발자 도구 Network/Console에서 CORS 오류와 preflight(OPTIONS) 응답 헤더를 확인한다.
  4. Authorization 헤더를 붙이는 요청(게스트가 아닌 상태, AG-AUTH-005 이후)도 preflight를 통과하는지 확인한다.
- 기대 결과: CORS 오류 없음, 응답 헤더에 허용 오리진 포함. 오류가 나면 Q-01 결과(프록시 사용)로 기록한다.
- 확인 방법: 콘솔 스크린샷, 응답 헤더 이름 목록(값에 비밀은 없음).
- 되돌릴 수 없음: 아니오(읽기 요청).
- 플랫폼 차이: Web 한정.
