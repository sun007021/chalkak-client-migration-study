# 에이전트 시나리오: NOTI, PUSH

[catalog/notification-push.md](../catalog/notification-push.md)에서 구분이 `A`인 TC를 서브에이전트가 시뮬레이터·에뮬레이터·브라우저와 개발 서버에서 직접 확인하는 절차다. 공통 전제(개발 서버 주소, 테스트 계정은 "실행 시 사용자에게 받은 계정", 비밀값 비기록, 사용자 Mac에서 실행, 결과를 parity-matrix에 반영)는 [boot-auth.md의 공통 전제](boot-auth.md#공통-전제-이-문서의-모든-시나리오)와 같다.

**푸시 발송 수단에 관한 주의**: 서버의 푸시 발송 경로(SQS, FCM)는 원본 가이드에서 "실제 AWS·Firebase·기기 수신, 서버 배포 미확인"으로 남아 있다([api-contract §7.1](../../reference/api-contract.md)). 실제 푸시를 보낼 수단(관리자 콘솔의 공지·주제 푸시 즉시 발송, 게시물 승인·반려, AI 리뷰 완료)은 에이전트가 가질 수 없으므로 **시나리오 실행 전에 사용자에게 발송 수단을 요청**한다. 수단이 없으면 시뮬레이터의 `xcrun simctl push` 또는 Android의 FCM 테스트 메시지·`adb` 인텐트로 payload만 흉내 내는 보조 확인을 하고, 결과 기록에 "실제 서버 푸시 도착은 미확인"이라고 명시한다. 흉내 확인은 A✓가 아니라 보조 통과로만 기록한다.

## NOTI

### AG-NOTI-001 실서버 알림함 조회, 읽음 처리, 미읽음 점

- 대응 TC: TC-NOTI-056
- 사전 조건: **실행 시 사용자에게 받은 카카오 계정**으로 로그인한 회원. 이 계정의 알림함에 최소 2건(미읽음 승인/반려/공지/AI 결과 중 하나 이상)이 있어야 한다. 없으면 사용자에게 알림을 만들어 달라고(관리자 승인·반려 또는 공지) 요청한다. 알림은 생성 후 30일이 지나면 사라지므로 최신 것이어야 한다. 개발 서버 정상.
- 단계:
  1. 홈에서 알림 벨에 미읽음 점이 있는지 캡처한다.
  2. 사용자에게 받은 토큰으로 `GET /notifications/unread-status`와 `GET /notifications?page=1&pageSize=20`을 읽기 전용으로 조회해 `hasUnread`와 목록을 기록한다(토큰 비기록).
  3. 벨을 탭해 알림 목록을 열고 서버 목록(제목, 본문, 읽음 여부, 시각)과 비교한다. 시각이 KST "M월 d일 HH:mm"인지, 호스트 시뮬레이터 시간대를 바꿔도 같은지 확인한다(시간대 변경은 시뮬레이터 설정에서).
  4. 미읽음 알림 하나를 탭한다. 유형별 이동(승인 → 게시물 상세, AI 결과 → 게시물 상세와 AI 시트, 반려/공지 → 알림 상세)을 확인한다.
  5. 뒤로 가서 목록에서 해당 항목이 읽음으로 바뀌었는지, 홈으로 돌아왔을 때 미읽음 점이 서버 `hasUnread`와 일치하는지 확인한다.
  6. 모든 미읽음을 읽은 뒤 점이 사라지는지 확인한다.
  7. 목록 끝까지 스크롤해 다음 페이지가 필요한 경우 한 번만 로드되는지 확인한다.
- 기대 결과: 목록·읽음 상태·미읽음 점이 서버 API 조회 결과와 일치한다. 이동 목적지가 type과 맞다. 시각이 시간대 설정과 무관하게 KST로 같다. 오류 토스트 없음.
- 확인 방법: 스크린샷(점 전·후, 목록, 상세), 서버 조회 결과와 화면 비교표, 디버그 로그에서 PATCH /notifications/{id}/read 호출 수(항목당 1회).
- 되돌릴 수 없음: 예(읽음 처리는 되돌릴 수 없으며 최초 readAt이 고정된다). 읽음 처리해도 되는 테스트용 알림만 사용한다.
- 플랫폼 차이: iOS 시뮬레이터, Android 에뮬레이터, 웹 브라우저(웹은 푸시 없이 알림함만 동일하게 제공). 시간대 변경 방법이 다르다(iOS 시뮬레이터는 호스트 시간대를 따르고 Android 에뮬레이터는 설정 앱).

### AG-NOTI-002 실제 반려 알림 상세의 사진과 사유 표시

- 대응 TC: TC-NOTI-057
- 사전 조건: 사용자 또는 관리자가 테스트 계정(실행 시 사용자에게 받은 계정)의 게시물을 관리자 콘솔에서 **반려 사유와 함께 반려**한 직후 상태. 반려는 사람이 해야 하는 작업이라 에이전트가 만들 수 없으며, 이미 반려 알림이 있다면 재사용한다. 개발 서버 정상.
- 단계:
  1. 알림 목록에서 반려 알림을 연다.
  2. 본인 사진 원본과 "반려 사유" 섹션이 읽기 좋게 보이는지, 긴 사유가 줄바꿈·스크롤로 잘리지 않는지 확인한다.
  3. "새로 올리기" 버튼이 없고 "알림함으로" 버튼으로 목록에 돌아가는지 확인한다.
  4. 네트워크를 끊고 같은 알림을 열어 오류/다시 시도 상태를 확인한다.
- 기대 결과: 사진과 사유 전문이 보이고 레이아웃이 깨지지 않는다. 새로 올리기 버튼 없음. 오프라인은 다시 시도 가능한 상태.
- 확인 방법: 스크린샷 비교(플랫폼 안에서 시각 판단, 플랫폼 간은 인상 기록), 서버 `GET /notifications/{id}` 응답의 `rejectionReason` 텍스트와 화면 텍스트 비교.
- 되돌릴 수 없음: 아니오(상세 조회는 읽음 처리하지 않는다). 단 반려 처리 자체는 관리자 작업으로 되돌릴 수 없다.
- 플랫폼 차이: iOS 시뮬레이터, Android 에뮬레이터, 웹 브라우저. 이미지 비율·여백 인상을 각각 기록한다.

## PUSH

### AG-PUSH-001 알림 권한 시스템 다이얼로그

- 대응 TC: TC-PUSH-074
- 사전 조건: 앱 신규 설치(OS 알림 권한 미결정). iOS 시뮬레이터(권한 초기화는 앱 삭제 후 재설치 또는 시뮬레이터 설정 재설정), Android 에뮬레이터는 API 33 이상(POST_NOTIFICATIONS)과 API 32 이하를 각각 준비한다. **실행 시 사용자에게 받은 카카오 계정**의 가입된 회원으로 로그인한다. 개발 서버 정상.
- 단계:
  1. 로그인 직후 첫 홈 진입에서 OS 권한 다이얼로그(또는 앱 안내)가 한 번 뜨는지 확인한다. 이전 설치에서 한 번 안내했다면 재설치로 플래그를 초기화한다.
  2. "허용"을 선택하고 설정 탭의 푸시 알림 토글 3개가 모두 켜짐인지, 서버 `GET /notification-settings`(사용자에게 받은 토큰, 읽기 전용)도 모두 true인지 확인한다.
  3. 앱 삭제 후 재설치해 다시 로그인하고 이번에는 "허용 안 함"을 선택한다. 설정 탭의 토글이 서버에 어떤 값으로 저장됐는지 확인한다(최초 안내 선택이 세 설정을 같은 불리언으로 저장하는 규칙, 거부면 모두 false).
  4. 앱을 종료했다 다시 열어 권한 안내가 다시 뜨지 않는지 확인한다.
  5. Android 12 이하 에뮬레이터에서는 런타임 권한 다이얼로그가 뜨지 않고 홈이 열리는지 확인한다.
  6. 확인 후 서버 토글 값을 모두 true로 원복한다.
- 기대 결과: 권한 요청은 인증 사용자의 첫 홈 진입에서 1회. 허용 → 토글 3개 true 저장, 거부 → false 저장이고 앱은 정상 동작. 재시작해도 반복되지 않는다. Android 12 이하는 요청 없음. 게스트로는 요청이 뜨지 않는다.
- 확인 방법: 시스템 다이얼로그 스크린샷, 서버 `GET /notification-settings` 응답 값 비교, 디버그 로그에서 PATCH /notification-settings 요청 바디(세 필드)와 상태 204.
- 되돌릴 수 없음: 아니오(설정 값은 되돌릴 수 있다. 6단계에서 원복).
- 플랫폼 차이: iOS는 시스템 권한 → 설정 저장, Android 13+는 POST_NOTIFICATIONS, Android 12 이하와 Web은 런타임 권한 없음(Web은 푸시를 하지 않으므로 이 시나리오를 수행하지 않고 생략을 기록한다).

### AG-PUSH-002 백그라운드 상태 푸시 도착과 탭 이동

- 대응 TC: TC-PUSH-075
- 사전 조건: AG-PUSH-001이 끝나 OS 권한이 허용된 상태. 기기에서 로그인된 회원이고 앱을 홈 화면으로 보내 백그라운드에 둔다. 개발 서버에서 푸시를 보낼 수단을 사용자에게 요청해 둔다(위 주의 참고). 서버 푸시 설정(주제·승인·반려·AI)은 모두 켜짐. 푸시 기기 등록이 성공한 상태.
- 단계:
  1. 백그라운드에서 type별 푸시를 하나씩 받는다: TOPIC, POST_APPROVED, POST_REJECTED, AI_REVIEW_COMPLETED(또는 FAILED), NOTICE.
  2. 각 알림이 OS 알림 센터에 도착하는 데 걸린 시간을 기록하고 제목·본문을 캡처한다.
  3. 알림을 탭해 앱이 열린 뒤의 화면을 확인한다: TOPIC → 홈 맨 위, POST_APPROVED → 게시물 상세, AI → 게시물 상세와 AI 시트 자동 열기, POST_REJECTED/NOTICE → 알림 상세.
  4. 각 탭 이후 알림함에서 해당 알림이 읽음으로 바뀌었는지(TOPIC 제외), 홈 알림 벨의 점이 갱신됐는지 확인한다.
  5. 같은 알림을 두 번 탭하는 경우(알림 센터에 남은 중복)를 확인한다.
- 기대 결과: 푸시가 실제로 도착하고 탭하면 D-11의 목적지 표대로 이동한다. 읽음 처리 후 이동하며 TOPIC은 읽음 호출이 없다. 중복 탭해도 앱이 깨지지 않는다.
- 확인 방법: 알림 센터·화면 스크린샷, 디버그 로그에서 파싱된 type과 PATCH /notifications/{id}/read 호출, 서버 `GET /notifications` 조회로 readAt 확인.
- 되돌릴 수 없음: 예(승인·반려·공지 발송은 관리자 작업이고 읽음 처리는 되돌릴 수 없음. 푸시 발송 자체도 서버 이력에 남는다).
- 플랫폼 차이: iOS 시뮬레이터는 APNs 시뮬레이션(`xcrun simctl push`) 외에 실제 FCM 도착은 실기기가 필요할 수 있다. 시뮬레이터에서 실제 도착이 불가하면 그 사실을 기록하고 payload 흉내 결과만 보조 통과로 남긴다. Android 에뮬레이터는 Google Play 서비스가 있는 이미지에서 실제 FCM이 도착한다. Web은 푸시를 하지 않으므로 생략한다.

### AG-PUSH-003 포그라운드 상태 푸시 수신

- 대응 TC: TC-PUSH-075
- 사전 조건: AG-PUSH-002와 같고 앱이 포그라운드로 보이는 상태(홈). 발송 수단 필요.
- 단계:
  1. 홈이 보이는 동안 AI_REVIEW_COMPLETED 푸시를 받는다.
  2. 어떤 UI(배너, 시스템 알림, 아무것도 없음)가 뜨는지 캡처한다.
  3. 홈 알림 벨의 미읽음 점이 바로 갱신되는지 확인한다.
  4. 해당 게시물의 AI 피드백 시트를 보고 있는 중에 같은 게시물의 AI 푸시를 받아 표시가 생략되는지 확인한다(해당 시트를 열 수 있는 AI 완료 게시물이 있어야 함).
  5. OS 알림 권한을 끈 상태에서 다시 한 번 받아 아무것도 표시되지 않는지 확인한다(Android).
- 기대 결과: Android는 앱이 알림을 직접 만들어 표시한다(채널 "게시물 검수 알림", 본문이 비면 기본 문구). iOS는 willPresent 정책대로 표시. 수신 후 미읽음 점이 재조회로 갱신. 같은 게시물 AI 화면에서는 표시 생략(임시 규칙). 권한 꺼짐이면 표시 없음.
- 확인 방법: 스크린샷, 디버그 로그에서 unread-status 재조회 호출, 포그라운드 처리 분기 로그.
- 되돌릴 수 없음: 예(AG-PUSH-002와 같음).
- 플랫폼 차이: iOS는 포그라운드 표시 옵션을 앱이 결정하고 Android는 onMessageReceived에서 직접 알림 생성. 기존 앱에 iOS 포그라운드 정책이 정의되어 있지 않아([TC-PUSH-069] 결정 필요) 관찰 결과를 기록해 결정 근거로 쓴다. Web 생략.

### AG-PUSH-004 강제 종료(콜드 스타트) 상태 푸시 탭

- 대응 TC: TC-PUSH-075
- 사전 조건: AG-PUSH-002와 같고 앱을 앱 전환기에서 완전히 종료한 상태. 인증 세션 유지. 발송 수단 필요.
- 단계:
  1. 앱을 강제 종료한다.
  2. POST_APPROVED, AI_REVIEW_COMPLETED, NOTICE 푸시를 하나씩 받고 각각 탭한다.
  3. 앱이 시작되고 스플래시 → 메인 준비 후 목적지로 이동하는지 확인한다(이동 도중 홈이 한 번 비치는지도 기록).
  4. 이동은 정확히 1회인지(뒤로 가면 홈으로 한 번에 오는지) 확인한다.
  5. 로그아웃 상태에서 앱을 종료하고 푸시를 탭해 앱만 열리고 목적지로 가지 않는지 확인한다.
- 기대 결과: 메인이 준비될 때까지 이동이 보류된 뒤 1회만 목적지로 이동. 로그아웃 상태 탭은 폐기. 크래시 없음.
- 확인 방법: 화면 녹화/스크린샷 시퀀스, 디버그 로그의 보류·소비 이벤트.
- 되돌릴 수 없음: 예(읽음 처리, 푸시 발송 이력).
- 플랫폼 차이: iOS는 콜드 스타트 시 launchOptions/userInfo, Android는 Intent extras(`google.message_id`)로 판별. 프로세스가 죽은 상태의 복원 방식이 다르므로 두 경로를 각각 확인한다. Web 생략.

### AG-PUSH-005 로그아웃 후 푸시 미수신과 설정 OFF 시 미수신

- 대응 TC: TC-PUSH-076
- 사전 조건: AG-PUSH-002와 같고 푸시 기기 등록이 성공한 로그인 상태. 발송 수단 필요. 서버 설정은 처음에 모두 켜짐.
- 단계:
  1. 설정 탭에서 "승인·반려 알림" 토글을 끄고 서버 `GET /notification-settings`(읽기 전용)로 false를 확인한다.
  2. 승인(또는 반려) 푸시를 발송해 도착하지 않는지, 알림함에는 기록되는지 확인한다.
  3. 토글을 다시 켠다.
  4. 로그아웃한다.
  5. 같은 기기로 승인 푸시를 발송해 도착하지 않는지 확인한다(서버가 세션과 함께 기기 행을 삭제).
  6. 다시 로그인한 뒤 새로 푸시가 도착하는지 확인한다(재로그인 시 새 등록).
  7. 다른 카카오 계정이 있다면 그 계정으로 로그인해 같은 FCM 토큰이 새 로그인에 이관되어 이전 계정 푸시가 오지 않는지 확인한다.
- 기대 결과: 설정이 꺼진 유형은 도착하지 않지만 알림함에는 남는다. 로그아웃 후에는 도착하지 않고 재로그인하면 다시 도착한다. 계정 전환 후 이전 계정 푸시는 오지 않는다.
- 확인 방법: 알림 센터 스크린샷(도착 없음 증거로 일정 시간 대기 후 캡처), 서버 알림함 조회, 디버그 로그에서 로그아웃 시 푸시 기기 해제 호출이 없고 재로그인 후 PUT /push-devices/current가 새로 호출되는 것.
- 되돌릴 수 없음: 예(푸시 발송 이력과 알림함 기록).
- 플랫폼 차이: iOS 시뮬레이터, Android 에뮬레이터. Web 생략. 토글 변경 토스트와 되돌림은 두 플랫폼에서 같다.

### AG-PUSH-006 iOS APNs 토큰의 FCM 등록

- 대응 TC: TC-PUSH-077
- 사전 조건: iOS 시뮬레이터(sandbox APNs) 또는 실기기. Firebase 설정 파일이 있는 빌드(없으면 Q-16에 따라 이 시나리오는 "차단"으로 기록). **실행 시 사용자에게 받은 카카오 계정**의 가입된 회원. 개발 서버 정상.
- 단계:
  1. 앱을 신규 설치하고 로그인한다. OS 알림 권한을 허용한다.
  2. 디버그 로그에서 APNs 토큰 수신, FCM 토큰 발급, PUT /push-devices/current 요청과 204 응답을 확인한다(토큰 값은 기록하지 않고 존재 여부와 길이만 기록).
  3. 앱을 다시 시작해 같은 등록이 다시 시도되는지(중복 제거 상태에 따라 요청 수) 확인한다.
  4. 가능하면 AG-PUSH-002와 연결해 실제 푸시가 이 기기에 도착하는지 확인한다.
- 기대 결과: APNs 토큰이 FCM 토큰으로 이어지고 등록이 204로 성공한다. 재시작 시 등록이 다시 시도되어도 오류가 없다. 시뮬레이터가 sandbox 타입으로 동작한다.
- 확인 방법: 디버그 로그(마스킹), 서버 푸시 도착 여부(AG-PUSH-002 연계).
- 되돌릴 수 없음: 아니오(기기 등록은 갱신 가능한 상태).
- 플랫폼 차이: iOS 한정(`FirebaseAppDelegateProxyEnabled=false` 환경에서 APNs 토큰을 수동 전달). Android는 FCM 토큰만 사용하므로 같은 확인을 AG-PUSH-002의 등록 로그로 갈음한다. Flutter·RN iOS는 플러그인이 APNs 토큰 전달을 대신하는지 확인한다.
