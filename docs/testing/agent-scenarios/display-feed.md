# 에이전트 시나리오: 전시·게시물 상세·좋아요(DISP, FEED, LIKE)

시각·제스처 판단과 개발 서버 확인이 필요한 항목이다. 대응 TC는 [catalog/display-feed.md](../catalog/display-feed.md)이다.
공통 규칙(모든 시나리오): 서버는 개발 서버 `https://chalkak-dev.pysun.kr/api/v1/`이다. 테스트 계정은 **실행 시 사용자에게 받은 카카오 계정**을 쓰며 문서·로그·스크린샷 파일명·커밋에 계정 정보와 토큰을 적지 않는다. 서버 API 조회가 필요하면 앱 디버그 로그나 사용자가 알려 준 값을 환경변수(`CHALKAK_ACCESS_TOKEN` 등)로만 다루고 출력에 남기지 않는다. 클라우드 컨테이너의 `curl`은 프록시 때문에 개발 서버에 닿지 않으므로(strategy §6) 사용자 Mac의 시뮬레이터·에뮬레이터와 Mac 터미널에서 실행한다. 스크린샷은 `agent-runs/<날짜>/<플랫폼>/AG-<영역>-NNN-<단계>.png`처럼 저장하고 계정 정보가 보이면 가린다. 결과는 패리티 매트릭스의 `A✓`로 기록한다. 플랫폼은 iOS, Android, Flutter(iOS·Android), React Native(iOS·Android), Web 순서로 같은 시나리오를 수행하고, 아래 "플랫폼 차이"에 적은 곳만 단계가 다르다.

### AG-DISP-001 개발 서버 실데이터로 전시 탐색

- **대응 TC**: TC-DISP-062
- **사전 조건**:
  - 로그인 상태이며 개발 서버에 `2026-09-17` 이후 여러 날의 전시 데이터가 있다(없는 날짜는 빈 상태 확인으로 대체).
  - 오늘 전시에 20장 넘는 사진이 있으면 무한 스크롤 확인이 가능하다.
- **단계**:
  1. 전시 탭을 열고 오늘 전시의 최신순·인기순·랜덤순을 차례로 선택해 스크린샷을 남긴다.
  2. 목록을 끝까지 스크롤해 다음 페이지가 이어서 로드되는지, 중복 사진이 없는지 본다.
  3. 이전 날짜 버튼으로 하루씩 과거로 이동한다. 과거 날짜는 정렬 탭이 숨고 상위 5개 추천 카드가 보이는지 확인한다.
  4. 날짜 선택 휠로 2026-09-17(최초 전시일)까지 이동하고 이전 버튼이 더 이상 동작하지 않는지 확인한다.
  5. 주제가 없는 날짜가 있으면 그 날짜로 이동해 기존 전시가 유지되는지 본다.
  6. 오늘로 돌아와 직전 정렬이 복원되는지, 사진을 탭해 상세로 갔다가 뒤로 와서 스크롤 위치가 유지되는지 확인한다.
  7. 게스트로 전환해 전시 목록은 보이고 사진 탭 시 "게시물 피드를 보려면 로그인이 필요해요"가 뜨는지 확인한다.
- **기대 결과**(관찰 가능한 것):
  - 2열 메이슨리가 사진 비율대로 배치되고 헤더 접힘·추천 카드·정렬 탭이 어색하지 않다.
  - 무한 스크롤이 끊기거나 같은 사진이 반복되지 않는다.
  - 최초 전시일에서 더 이전으로 갈 수 없고 오늘 이후로도 갈 수 없다.
- **확인 방법**:
  - 스크린샷 세트와 화면 녹화.
  - 공개 API로 대조: `GET /posts?topicDate=<날짜>&sort=popular`의 상위 5개 ID가 추천 카드와 같고 `sort=random` 응답의 `randomSeed`가 2페이지 요청(`page=2&randomSeed=…`)에 쓰이는지 앱 로그로 본다.
- **되돌릴 수 없음 여부**: 해당 없음(조회만 한다).
- **플랫폼 차이**:
  - Web: 마우스 휠 스크롤과 창 크기 변화(열 수)를 함께 확인한다.
  - iOS 시뮬레이터/Android 에뮬레이터 모두 가능하다.

### AG-FEED-001 핀치 줌과 뒤로 스와이프 감각

- **대응 TC**: TC-FEED-054
- **사전 조건**:
  - 게시물 상세로 들어갈 수 있는 게시물이 하나 이상 있다(전시에서 아무 사진).
  - 실기기가 있으면 실기기를 우선한다. 시뮬레이터 핀치는 iOS는 Option+드래그, Android 에뮬레이터는 Ctrl+드래그다.
- **단계**:
  1. 상세에서 사진을 핀치로 확대한다. 4배에서 더 커지지 않는지 본다.
  2. 손을 떼면 1배로 부드럽게 돌아오는지 본다.
  3. 확대한 상태에서 두 손가락으로 이동해 이미지 가장자리에서 멈추는지 본다.
  4. (iOS) 아래로 뒤로 스와이프를 천천히 끌다가 놓아 취소해 보고, 충분히 끌어 완료해 본다. 가로로 흔들면서 끌어도 어색하지 않은지 본다.
  5. 사진 비율이 다른 게시물(세로·가로·정사각)에서 같은 동작을 반복한다.
- **기대 결과**(관찰 가능한 것):
  - 손가락을 따라가는 느낌에 지연이나 튐이 없고 복귀 애니메이션이 자연스럽다.
  - 확대·이동 중 스크롤이나 뒤로가기와 충돌하지 않는다.
- **확인 방법**:
  - 화면 녹화(60fps 이상)와 구간별 스크린샷.
  - 평가 기준: 끊김 없음, 한계에서 멈춤, 복귀 시간 0.3~0.7초 범위 안.
- **되돌릴 수 없음 여부**: 해당 없음.
- **플랫폼 차이**:
  - iOS 뒤로 스와이프는 iOS 전용 제스처다. 다른 플랫폼은 시스템 뒤로 제스처가 정상 동작하는지만 확인한다.
  - Web: 트랙패드 핀치와 Ctrl+휠 줌을 확인하고 터치 없는 환경에서는 줌 확인을 생략한다.

### AG-FEED-002 본인 게시물 제목 수정과 삭제 실서버 확인

- **대응 TC**: TC-FEED-055
- **사전 조건**:
  - 오늘 주제에 내 게시물이 하나 있다(AG-UPL-001로 만든 PENDING 또는 APPROVED 게시물). VALIDATING 상태에서는 삭제할 수 없으므로 PENDING 이후에 수행한다.
  - 게시물 ID는 기록 탭 또는 앱 로그로 얻는다.
- **단계**:
  1. 기록 탭에서 오늘 사진을 선택하고 "피드에서 보기"로 상세를 연다(PENDING이면 기록에서 상세가 닫혀 있으므로 APPROVED일 때만 가능, 아니면 이 단계는 보류).
  2. 제목 수정 버튼을 눌러 "테스트제목"을 저장하고 토스트를 확인한다.
  3. 이모지 10개를 입력해 저장하고, 11번째 입력이 막히는지 확인한다.
  4. 제목을 공백만 입력해 저장하면 "무제"가 되는지 확인한다.
  5. 삭제 버튼 → 확인창 → 삭제를 실행하고 토스트와 전시·기록·홈에서의 제거를 확인한다.
  6. 삭제 후 홈 히어로가 Empty로 돌아가는지, 업로드 진입이 다시 열리는지 확인한다(주제가 아직 OPEN일 때).
- **기대 결과**(관찰 가능한 것):
  - 수정 응답이 즉시 상세·전시·기록에 반영되고 서버 값과 같다.
  - 삭제 후 어떤 화면에도 게시물이 남지 않고 같은 주제로 다시 업로드할 수 있다.
- **확인 방법**:
  - 각 단계 스크린샷.
  - 사용자가 알려 준 토큰으로 Mac 터미널에서 `GET /posts/{id}`를 조회해 `title`을 확인하고 삭제 후에는 404인지 본다(토큰은 출력하지 않는다).
  - `GET /posts/today`로 `isPosted` 값 변화 확인.
- **되돌릴 수 없음 여부**: 제목 수정은 다시 수정해 되돌릴 수 있다. **삭제는 되돌릴 수 없다**(서버에 논리 삭제 기록이 남고 업로드 행도 남는다). 주제가 아직 OPEN이면 같은 주제로 다시 올릴 수 있어 슬롯은 회복된다. 실행 전 사용자에게 삭제해도 되는 게시물인지 확인한다.
- **플랫폼 차이**:
  - Web: 수정/삭제 확인창이 브라우저 다이얼로그가 아닌 앱 UI인지만 확인한다.

### AG-LIKE-001 좋아요 연타와 서버 최종 상태 일치

- **대응 TC**: TC-LIKE-035
- **사전 조건**:
  - 로그인 상태. 내가 좋아요하지 않은 타인의 APPROVED 게시물이 전시에 있다.
  - 원래 좋아요 상태를 시작 전에 기록한다(`isLiked`, `likeCount`).
- **단계**:
  1. 전시에서 해당 사진의 하트를 한 번 탭해 즉시 반영(하트·개수)을 확인한다.
  2. 서버 조회로 `isLiked=true`, `likeCount`가 +1인지 확인한다.
  3. 하트를 빠르게 3번 연타(on·off·on)하고 2초 기다린 뒤 서버 상태와 화면 상태를 비교한다.
  4. 하트를 눌러 좋아요를 취소하고 서버 상태를 확인한다.
  5. 비행기 모드를 켜고 하트를 탭해 롤백과 토스트 "좋아요를 반영하지 못했어요"를 확인한다. 비행기 모드를 끈다.
  6. 시작 전 상태와 같은지 확인하고 아니면 원래 상태로 되돌린다.
- **기대 결과**(관찰 가능한 것):
  - 탭 즉시 화면이 바뀌고 서버 최종 상태가 화면과 항상 같다.
  - 오프라인 실패 시 이전 상태로 돌아가고 토스트가 한 번 뜬다.
- **확인 방법**:
  - 사용자가 알려 준 토큰으로 `GET /posts/{id}`를 조회해 `isLiked`·`likeCount`를 비교한다(토큰 비출력).
  - 화면 녹화와 앱 요청 로그(PUT/DELETE 횟수).
- **되돌릴 수 없음 여부**: 좋아요는 취소로 되돌릴 수 있다. 타인 게시물의 `likeCount`가 잠시 변하므로 마지막 단계에서 원래 상태로 복구한다.
- **플랫폼 차이**:
  - Web: 비행기 모드 대신 개발자 도구의 오프라인 설정을 쓴다.
  - iOS 시뮬레이터는 호스트 네트워크를 끊거나 Network Link Conditioner의 100% Loss 프로필을 쓴다.
